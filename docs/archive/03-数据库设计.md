## 1. 文档目的与设计原则

### 1.1 文档目的

本文件定义 `rocket_manage`（KSP 发射计划与任务记录管理工具）的**完整持久化模型**，是后续三份文档的共同地基：

| 下游文档 | 依赖本文件的部分 |
|---|---|
| `04-接口与路由设计` | 视图/表单操作的模型与字段、`select_related` 关联路径 |
| `05-页面交互设计` | 每个页面展示的字段、枚举的可读标签、`code` 短码展示规则 |
| `06-核心计算设计` | 计算所需的输入字段（`sma`/`mu`/`capacity`/`isp_*`/`dry_mass`）、派生量与落库量的边界 |
| `07-重构方案与实施计划` | 第 7、8 节（被移除的旧字段、新旧字段映射表） |

**关键约定**：**建模由 Django migrations 管理，模型定义使用 Django ORM，不写裸 SQL DDL。** 旧项目的 `arock.sql`（`DROP DATABASE` + `CREATE TABLE`）被彻底取代（见第 10 节）。

### 1.2 设计原则

| # | 原则 | 说明与取舍 |
|---|---|---|
| P-01 | **以 3NF 为目标** | 所有非主属性完全函数依赖于主键，不存在部分依赖；`PartCatalog` 作为 1:1 超类消除多值依赖（详见第 6 节） |
| P-02 | **适度反规范化，且必须书面论证** | 每一处反规范化都在第 6 节列出并给出理由。原则：**只接受"派生量的一次性抄录快照"，不接受"可从级配置算出的权威值"**（这正是旧 `Carrier` 五个字段被移除的判据） |
| P-03 | **每张业务表都有业务短码 `code`** | `CharField(24)`、`unique=True`、`db_index=True`；供玩家阅读、检索、打印；格式见基准文档 4.15。取代旧 `CHAR(5)` 定长编号（编号耗尽 + 与表单校验自相矛盾的缺陷） |
| P-04 | **主键统一 `BigAutoField`** | `DEFAULT_AUTO_FIELD = 'django.db.models.BigAutoField'`；不暴露自增语义给玩家，玩家只看 `code` |
| P-05 | **时间统一使用 KSP 游戏时间 `UT`** | 全部为 `FloatField`（游戏内秒，自存档开始累计），**不使用 `DateField`/`DateTimeField` 表达游戏时间**。现实世界时间仅以 `created_at`/`updated_at` 形式出现在审计字段，不参与业务语义 |
| P-06 | **单位统一** | 质量 **吨（t）**、距离 **米（m）**、速度 **m/s**、推力 **千牛（kN）**、比冲 **秒（s）**、角度 **度（°）**、造价 **根币（√）**、燃料容量 **单位（unit）**。全部 `FloatField`，不引入小数类型（见 2.3-⑤） |
| P-07 | **派生量不落库** | 轨道周期、近/远拱点、轨道速度、LEO 运力、箭体总质量、最大推力、推重比**一律实时计算**，避免与权威输入漂移。仅允许"带提示的抄录快照"（`Spacecraft.cached_period_sec`、`CarrierModel.max_payload_mass`） |
| P-08 | **能由数据库强制的约束，绝不用 Python 兜** | 表内 `CHECK`、`UNIQUE`、`FOREIGN KEY` 一律下推到 DB（SQLite 支持表级 CHECK 与外键，Django 自动开启 `PRAGMA foreign_keys=ON`） |
| P-09 | **跨表校验与需友好提示的规则放模型 `clean()`** | SQLite 不支持 `ALTER TABLE ADD CONSTRAINT`，且 CHECK 无法子查询引用他表；同时业务规则需要中文错误提示。故跨表规则集中在 `Model.clean()`（详见 2.4） |
| P-10 | **删除策略显式化** | 每个 `on_delete` 逐字段指定，遵守基准文档 4.16 的策略总表；不依赖默认 `CASCADE` |
| P-11 | **枚举用 `TextChoices`** | 数据库存可读字符串（如 `'PLANNED'`）而非整数编码，Admin/`dumpdata` 输出自解释，可读性优先；代价是列宽换空间，自用工具可忽略 |
| P-12 | **不用 `GenericForeignKey`** | 多态用「`type` 判别列 + 双/五可空 FK + 恰好一个非空的 CHECK」实现；`ContentType` 多态无法建立数据库级外键与 CHECK，且 Admin 的 Generic 内联会绕过约束（基准 5.3 已规避） |
| P-13 | **v1 不做软删除** | 删除即删除；业务表的"历史不可丢"由 `on_delete=PROTECT` 表达（发射历史保护火箭/载荷/发射场） |
| P-14 | **不在表中存计算中间量** | 如"各级质量构成"（基准 8.1）由 `services/deltav.py` 从 `Stage`/`StageTank`/`Engine`/`FuelTank` 现算 |

## 2. 数据库选型说明

### 2.1 选型结论：SQLite（`db.sqlite3`）

| 维度 | SQLite 的表现 | 对本项目的意义 |
|---|---|---|
| 部署形态 | 单文件 `db.sqlite3`，零安装零服务 | 与"游戏记录本"形态一致：拷走文件即完成备份/换机 |
| 并发 | 单写者、库级写锁 | 单人单机自用，无并发压力（基准 R-06 已声明不做并发硬化） |
| 事务 | 完整支持 ACID（WAL 可选） | `transaction.atomic()` 可用；级 FormSet 保存可整体回滚 |
| 外键 | 支持，但**默认关闭**，需 `PRAGMA foreign_keys=ON` | Django 连接初始化即执行该 PRAGMA，因此基准 4.16 的 `PROTECT`/`CASCADE` 策略**真的会被数据库强制** |
| 约束 | 支持表级 `CHECK`/`UNIQUE`/`PRIMARY KEY`/外键；**不支持 `ALTER TABLE ADD CONSTRAINT`** | 见 2.3-①；Django 通过"重建表"方式演进约束 |
| 依赖 | Python 标准库 `sqlite3` 内置 | `requirements.txt` 无需数据库驱动，**PyMySQL 被删除**（基准 11.2-③） |

### 2.2 未来换 MySQL 8.4 的代价评估

基准决策 D-03 结论：**约 1 小时改连接串 + 必须做数据迁移**。本设计的落地口径如下：

| 工作项 | 工作量 | 说明 |
|---|---|---|
| 安装驱动 | 5 min | `pip install mysqlclient`（或 `PyMySQL` + `pymysql.install_as_MySQLdb()`） |
| 改 `DATABASES` | 5 min | `config/settings/prod.py` 中把 `ENGINE` 换为 `django.db.backends.mysql`，补 `NAME/USER/PASSWORD/HOST/PORT/OPTIONS` |
| 模型层适配 | ≈ 40 min | 逐个检查：`CharField(max_length)` 语义收紧（MySQL 真的截断/报错）、`unique` + 长 `CharField` 的索引长度、`TextField` 索引限制、排序规则（`utf8mb4_0900_ai_ci` 不区分大小写会改变 `code` 的唯一性判定 → 建议 `code` 用 `utf8mb4_bin`）。**本设计刻意避开了 SQLite 特有类型，故没有类型级重写工作** |
| **数据迁移** | **必须** | ⚠️ **不是换连接串就完事**：两种存储引擎的数据不会自动搬运。标准做法是 `python manage.py dumpdata --natural-foreign --indent 2 -o backup.json` → 切库 → `migrate` → `loaddata backup.json`。注意：① `dumpdata` 会带上 `contenttypes`/`auth.permission`，建议 `--exclude contenttypes --exclude auth.permission`；② 自增主键会原样保留，故 `loaddata` 后需 `sqlsequencereset` 重置 MySQL 自增计数器；③ `Body` 自引用 FK 依赖 `--natural-foreign` 或夹具里的自然键（本设计为 `Body` 实现了 `natural_key`，见 3.2） |
| 合计 | 约 1 小时（不含数据核对） | v1 不做（D-03） |

> **换库的真正成本不在 ORM，而在数据搬运与核对。** 本设计把"跨表 CHECK 放 `clean()`"的副作用（MySQL 本是支持跨表约束的更少的那一类）也一并接受，就是为了让换库只发生一次、且代价可预估。

### 2.3 SQLite 的关键限制及其对本设计的影响

> 这一节是本设计的**约束来源清单**：第 3 节的代码中每一处"没写成 DB 约束"的决定，都能回到这里找到理由。

#### ① `ALTER TABLE ADD CONSTRAINT` 支持有限；CHECK 约束变更需重建表

- SQLite 的 `ALTER TABLE` 只支持 `RENAME` / `ADD COLUMN` / `DROP COLUMN` / `RENAME COLUMN`，**不支持增删约束**。
- Django 的处理方式：当 `makemigrations` 检测到约束增删时，自动生成"建新表 → 复制数据 → 删旧表 → 改名"的重建迁移（`migrations.AlterModelTable` 风格的空壳下由 schema editor 完成）。表一重建，**其上的索引与外键引用都会一并重做**。
- **对本设计的影响**：
  - 表内 `CHECK`（如 `fueltank_capacity_nonneg`、`stage_order_positive`、`program_priority_range`）**只在"纯表内、单行、无子查询"时才写成 `CheckConstraint`**——值得进 DB，因为它们廉价且永不漂移。
  - **任何需要引用其他表的规则都不写成 CHECK**（SQLite 的 CHECK 表达式不允许子查询，见 ④/2.4），否则一旦规则调整就要付出重建表的代价。

#### ② 多个 `NULL` 在 UNIQUE 约束下互不冲突

- SQLite 遵循 SQL 标准：`UNIQUE` 索引中 `NULL` 与任何值（含另一个 `NULL`）**都不相等**，故含 `NULL` 的行可以任意多条共存。
- **这正是 `ProgramLink` 的 5 条 `UniqueConstraint` 能共存的原因**：
  - `uniq_program_carrier = UNIQUE(program, object_type, carrier)`。当一行是"载荷成员"时，`carrier` 为 `NULL` → 该行在 `uniq_program_carrier` 眼中是"含 NULL 的键"，不参与比较，不会与另一行"载荷成员"冲突。
  - 5 条约束各管一个对象列，于是同时获得：**同一计划内同类型对象不重复** + **一个对象不重复归属多个计划**，且不需要"部分索引"（partial index）那样的方言特性（`UniqueConstraint(condition=...)` 也能用，但没必要）。
- **同样的机制也让 `Stage` 的两条唯一约束共存**：`uniq_carrier_stage_order = UNIQUE(carrier, stage_order)` 与 `uniq_payload_stage_order = UNIQUE(payload, stage_order)` —— 一个火箭的级行 `payload` 为 `NULL`，不参与后者比较。
- ⚠️ **跨库注意**：MySQL 同样允许 `NULL` 在唯一索引中重复，故该设计**可移植**；但若将来改成 `null=False` + 哨兵值（如 `0`），唯一性语义会立刻崩塌并互相误伤。**这条推论写入模型注释。**

#### ③ 需要 `PRAGMA foreign_keys=ON`（Django 会开）

- SQLite 的外键**默认不强制**；不开启则 `on_delete=PROTECT` 形同虚设，`CASCADE` 也不会发生，`related_name` 反向查询看似正常但引用完整性已在被破坏。
- **Django 5.2 在建立每个 SQLite 连接时自动执行 `PRAGMA foreign_keys = ON`**（`django/db/backends/sqlite3/base.py` 的 `get_new_connection`），因此：
  - 基准 4.16 的删除策略表**由数据库强制执行**，旧项目 `manage.py:595` 的 `check_foreign_key()` 手工检查函数可以**彻底废弃**（基准 11.3）。
  - 由原始 `sqlite3` CLI 或第三方工具改库时，**必须手动 `PRAGMA foreign_keys=ON`**，否则可能写出孤儿行。运维提示写入 `07`。
  - `PROTECT` 触发的是 Python 侧 `ProtectedError`（Django 在删除前先查引用，避免依赖 DB 报错信息），因此**即使 PRAGMA 被关闭，Django ORM 层的 `PROTECT` 仍然生效**——这层冗余是我们希望保留的。

#### ④ 类型亲和性（type affinity）：`VARCHAR(24)` 不强制长度

- SQLite 的声明类型只是"亲和性提示"：`VARCHAR(24)` 不会拒绝 30 个字符的写入（只有 `CHECK(length(code) <= 24)` 才会）。
- **对本设计的影响**：
  - 所有长度限制（`code` 24、`name` 80、`series` 60、`experiment_type` 40 …）在 SQLite 下**靠 Django 校验（`max_length` + 表单 + `full_clean()` + `RegexValidator`）保证**，不是 DB 保证。
  - `code` 的格式校验必须落实到 `RegexValidator`（见 3.1 `CodeModel`），因为 DB 不会替我们挡。
  - 写入路径全部经 Django（Admin / Form / ORM），**不允许绕过 ORM 直接写库**；这使"长度靠 Django"成为可接受的设计，但必须在文档里写明（换 MySQL 后这一层会变成真实约束，是收紧而非放宽）。
  - 同理，`BooleanField` 在 SQLite 中实际存 `0/1`（`INTEGER` 亲和），`PositiveIntegerField` 存 `INTEGER`，与 Django 语义一致，无风险。

#### ⑤ 原生不支持精确 `NUMERIC`/`DECIMAL`：浮点比较需注意

- SQLite 只有 5 种存储类（`NULL/INTEGER/REAL/TEXT/BLOB`），`DecimalField` 会被映射到 `decimal` → 实际存 `REAL`，**丢失精确性**。
- **对本设计的影响**：
  - 全库**不使用 `DecimalField`**，一切连续量用 `FloatField`（float64，约 15–17 位十进制有效数字）。这对 KSP 量级（半径 10⁵–10⁶ m、μ ~10¹²–10¹⁸、Δv 10³–10⁴ m/s）**完全够用**。
  - **不在 SQL 中做浮点等值比较**。代码中禁止 `filter(dry_mass=1.25)` 之类写法，改用区间比较；`services/` 中的断言用 `pytest.approx`/`assertAlmostEqual`（基准 9.2 的验算样例已给出容差样例）。
  - 需要"不可比的精确值"的场景（造价、计数）**一律用整数字段**（`PositiveIntegerField`/`IntegerField`），回避浮点：`cost`、`budget`、`spent`、`engine_count`、`quantity`、`result_code`（含 `-1/-2`，用有符号 `IntegerField`）。
  - `CheckConstraint` 中的数值比较（如 `priority >= 1`）发生在整数列上，无风险。

### 2.4 为什么跨表校验放在 Django 模型 `clean()` 而非数据库 CHECK

**本设计明确把以下 6 类规则放进 `Model.clean()`（见第 3 节代码）**：

| # | 规则 | 涉及表 | 若强行用 CHECK 会怎样 |
|---|---|---|---|
| 1 | `FuelTank.wet_mass >= part.dry_mass`（基准 4.3） | `parts_fueltank` + `parts_partcatalog` | CHECK 表达式**不能含子查询**，无法读取 `part.dry_mass`；退一步用触发器则跨库不可移植、且 Django 不管理触发器 |
| 2 | `Spacecraft.sma > body.radius`（基准 4.14） | `spacecraft_spacecraft` + `core_body` | 同上：需要读 `body.radius` |
| 3 | `Site.latitude ∈ [-90, 90]`、`longitude ∈ [-180, 180]`（基准 4.10） | `sites_site` | **这一条技术上可以写成 CHECK**（纯单行），但为与经纬度的"业务语义错误提示"统一（前端要显示"纬度必须在 −90…90 之间"），仍放 `clean()`；`clean()` 会抛出带字段名的 `ValidationError`，而 CHECK 只会抛 `IntegrityError` |
| 4 | `FlightLog` 的状态-时间一致性（`PLANNED` ⇒ `actual_ut IS NULL`；`LAUNCHED/FAILED` ⇒ `actual_ut` 非空）（基准 4.11） | `launches_flightlog` | **技术上可写成 CHECK**（单行），但基准 4.11 明确要求"写在 `clean()` 而非 DB CHECK，便于给出友好错误提示"，且该规则会随 v1.1 的 `state` 增补而变——避免重建表（见 ①）。**但它的后半段"已发射必须有时间"仍补了一条 DB CHECK 作为兜底**（见第 11 节 `flight_actual_ut_required`），因为它是不可协商的不变量 |
| 5 | `Program.end_ut >= start_ut`（基准 4.12） | `programs_program` | 单行、可写 CHECK，但"两者都非空时"是条件式规则，且错误信息需要落到具体字段 |
| 6 | `Engine.thrust_vac >= thrust_asl`（基准 4.4）、`ScienceInstrument.transmit_efficiency ∈ [0,100]`（基准 4.5）、`Name`/`code` 正则与唯一性的友好提示 | 各表 | 有的是"更严格但合法数据可能存在"的启发式（某些引擎海平面数据缺失时 `thrust_asl` 为 0，`thrust_vac >= thrust_asl` 恒真；但若玩家录入异常值，应该警告而非拒绝），本质是**质量提示**而非硬约束 |

**统一理由（必须记住的三条）**：

1. **SQLite 能力限制**：`CHECK` 不能子查询引用他表（限制 ④/⑤ 的连带后果），跨表规则在 DB 层**写不出来**；且约束一旦要改就要重建表（限制 ①）。
2. **需要友好错误提示**：`ValidationError` 携带字段名与中文消息，能直接渲染在表单字段下（`05-页面交互设计` 的表单错误展示依赖此）；`IntegrityError` 只能显示"数据库错误"，对玩家毫无意义。
3. **需要按需触发**：跨表规则依赖"另一个对象当前的值"，只在保存时点校验即可。Django 的 `ModelForm` → `full_clean()` → `clean()` 链路天然把两层（字段级 → 模型级）串起来，**Admin 也走同一条链路**，不需要额外 wiring。

**代价与补偿**：`clean()` **不会在 `Model.save()` 中自动调用**（Django 的刻意设计）。因此：

- 所有写入口必须走 `ModelForm`/`ModelAdmin`（本项目如此，无裸 `save()`）；
- `services/` 与数据迁移脚本写入前显式调用 `full_clean()`；
- 涉及"不可协商的不变量"的规则，**再补一条 DB 级 CHECK 兜底**（如 `flight_actual_ut_required`、`spacecraft_eccentricity_range`），形成"DB 挡住脏数据 + `clean()` 给出好提示"的双层。

---

> **代码约定**
> - Django 5.2 语法；`CheckConstraint` **一律使用 `condition=` 关键字参数**（Django 5.1 起 `check=` 已弃用并改名，本文件不出现旧写法）。
> - 每个字段带 `verbose_name`（中文标签），关键字段带 `help_text`。

# core/mixins.py
"""公共抽象基类：时间戳 + 业务短码。

本模块只包含 abstract 模型，不产生任何数据库表。
"""
import re

from django.core.exceptions import ValidationError
from django.core.validators import RegexValidator
from django.db import models

# 基准文档 4.15：前缀-主体[-序号]，全大写 ASCII，总长 ≤ 24
CODE_PATTERN = r'^[A-Z0-9][A-Z0-9/\-]{1,22}[A-Z0-9]$'
CODE_REGEX = re.compile(CODE_PATTERN)

code_validator = RegexValidator(
    regex=CODE_PATTERN,
    message=(
        '短码格式非法：应为「前缀-主体[-序号]」，全大写 ASCII（允许 A-Z 0-9 / -），'
        '总长 3–24 字符，首尾必须是字母或数字。示例：LV-DAVY2B、SCP-2026-014、S/C-KERBIN-SAT1。'
    ),
)

CODE_PREFIX_HELP = (
    '前缀约定：BODY- 天体｜PART- 部件｜TANK- 燃料罐｜ENG- 引擎｜SCI- 科学设备｜'
    'LV- 火箭｜PL- 载荷｜PAD- 发射场｜SCP- 发射日志｜PRG- 计划｜S/C- 航天器。'
)


class TimeStampedModel(models.Model):
    """审计时间戳。

    ⚠️ 这里是**现实世界时间**（auto_now_add / auto_now），仅用于后台管理与排错，
    不参与任何业务语义。KSP 游戏时间一律用 FloatField 的 UT 字段表达（见各业务表）。
    """

    created_at = models.DateTimeField('创建时间', auto_now_add=True, db_index=True)
    updated_at = models.DateTimeField('更新时间', auto_now=True)

    class Meta:
        abstract = True


class CodeModel(models.Model):
    """业务短码基类：每张业务表都有玩家可读的 `code`。

    主键仍是 Django 默认的 BigAutoField `id`（D-05）；
    `code` 是**业务唯一键**，用于界面展示与检索。
    """

    code = models.CharField(
        '短码',
        max_length=24,
        unique=True,
        db_index=True,
        validators=[code_validator],
        help_text='业务唯一短码，格式「前缀-主体[-序号]」。' + CODE_PREFIX_HELP,
    )

    class Meta:
        abstract = True

    def clean(self):
        super().clean()
        if self.code:
            # SQLite 的 VARCHAR(24) 不强制长度（类型亲和性），这里补上长度校验
            if len(self.code) > 24:
                raise ValidationError({'code': '短码总长不得超过 24 个字符。'})
            if not CODE_REGEX.match(self.code):
                raise ValidationError(
                    {'code': '短码格式非法（需全大写 ASCII，形如 LV-DAVY2B、SCP-2026-014）。'}
                )
```

"""core app：天体（Body）。

`Body` 是唯一不继承 TimeStampedModel 的业务表之一（基准 4.0：
「除 Body/PartCatalog 外，主要业务表加 created_at/updated_at」）。

class Body(CodeModel):
    """天体（KSP 原版 17 个：Kerbol / Kerbin / Mun / Minmus / Duna / Ike / Eve / Gilly /
    Moho / Dres / Jool / Laythe / Vall / Tylo / Bop / Pol / Eeloo）。

    结构为**自引用树**（Kerbol → Kerbin → Mun）。数值全部可编辑：
    天体常数是数据而非硬编码，使用 RSS/OPM 等模组时重新采集（基准 R-01）。
    """

    name = models.CharField('天体名称', max_length=60, unique=True)
    name_en = models.CharField('英文名', max_length=60, blank=True)
    parent = models.ForeignKey(
        'self',
        verbose_name='母天体',
        null=True,
        blank=True,
        on_delete=models.PROTECT,  # 有子天体的天体不可删（基准 4.16）
        related_name='children',
        help_text='Kerbol 无母天体；Mun 的母天体是 Kerbin。',
    )
    radius = models.FloatField('赤道半径', null=True, blank=True, help_text='单位 m。Kerbin=600000')
    mu = models.FloatField(
        '标准重力参数',
        null=True,
        blank=True,
        help_text='标准重力参数 μ=GM，单位 m³/s²。周期计算必需（T=2π√(a³/μ)）。Kerbin≈3.5316e12',
    )
    soi_radius = models.FloatField(
        '影响球半径', null=True, blank=True, help_text='Sphere of Influence，单位 m。'
    )
    atmosphere_height = models.FloatField('大气高度', default=0, help_text='单位 m；无大气填 0。')
    has_atmosphere = models.BooleanField('有大气', default=False)
    sidereal_day = models.FloatField(
        '恒星日', null=True, blank=True, help_text='单位 s。**同步轨道与周期换算必须用恒星日**（基准 8.5）。'
    )
    solar_day = models.FloatField(
        '太阳日', null=True, blank=True, help_text='单位 s。仅用于显示层「天」换算，勿用于周期公式。'
    )
    surface_gravity = models.FloatField('表面重力', null=True, blank=True, help_text='单位 m/s²。')
    is_star = models.BooleanField('是恒星', default=False, help_text='仅 Kerbol 为 True。')
    is_reachable = models.BooleanField('可达', default=True, help_text='原版 KSP 无其他星系，全部可达。')
    sort_order = models.PositiveIntegerField('显示排序', default=0)
    description = models.TextField('备注', blank=True)

    objects = BodyManager()

    class Meta:
        verbose_name = '天体'
        verbose_name_plural = '天体'
        # ⚠️ 基准 4.1 原文写作 ['sort_order', 'depth_hint']，但字段清单中并无 depth_hint 列。
        # 本设计不新增字段，改用既有的 name 作为稳定次序（层级缩进由模型的 depth 属性渲染）。
        ordering = ['sort_order', 'name']
        constraints = [
            # 禁止自己当自己的母天体（表内、单行、无子查询 → 可以进 DB）
            models.CheckConstraint(
                condition=models.Q(parent__isnull=True) | ~models.Q(parent_id=models.F('id')),
                name='body_no_self_parent',
            ),
        ]
        indexes = [
            models.Index(fields=['parent', 'sort_order'], name='idx_body_parent_sort'),
        ]

    def __str__(self):
        return f'{self.name}（{self.code}）'

    def natural_key(self):
        return (self.code,)

    @property
    def depth(self):
        """在树中的层级（Kerbol=0，Kerbin=1，Mun=2…）。用于 Admin/模板缩进显示。"""
        level, node, guard = 0, self, 0
        while node.parent_id is not None and guard < 16:
            node = node.parent
            level += 1
            guard += 1
        return level

    @property
    def display_name(self):
        return '　' * self.depth + self.name

    def clean(self):
        super().clean()
        errors = {}
        if self.parent_id is not None and self.pk is not None and self.parent_id == self.pk:
            errors['parent'] = '母天体不能是自己。'
        if self.parent_id is not None and self.parent is not None:
            if self.parent_id == self.parent.parent_id:
                errors['parent'] = '母天体不能是自身的直接子天体（会形成二元环）。'
        if self.radius is not None and self.radius <= 0:
            errors['radius'] = '赤道半径必须大于 0。'
        if self.mu is not None and self.mu <= 0:
            errors['mu'] = '标准重力参数 μ 必须大于 0。'
        if self.atmosphere_height is not None and self.atmosphere_height < 0:
            errors['atmosphere_height'] = '大气高度不能为负。'
        if self.has_atmosphere and self.atmosphere_height == 0:
            errors['atmosphere_height'] = '标记「有大气」时大气高度应大于 0（Kerbin=70000）。'
        if not self.has_atmosphere and self.atmosphere_height:
            errors['atmosphere_height'] = '未标记「有大气」时大气高度应为 0。'
        if errors:
            raise ValidationError(errors)
```

class FuelTank(models.Model):
    """燃料罐（需求①）。

    ⚠️ **容量语义（基准 4.3，必须与 06 保持一致）**：
    `capacity` 是**燃料资源单位数**。质量换算恒定使用 `FUEL_UNIT_MASS = 0.005 t/单位`（即 **1 单位 = 5 kg**），**不存在「1 单位 ≈ 1 kg」的读法**（基准 v1.1 已删除该错误表述）。
    - `LF_OX`：`capacity` 为 **LF + OX 合计**单位；单位质量按 KSP 混合比折算，
      统一取 **0.005 t/单位**的**混合平均质量**。
    - 建模简化声明：**不做 LF/OX 分账**。对「本级总质量 → Δv」的计算足够精确，
      且与新版本 KSP 的 LF/OX 统一密度一致。
    - `SOLID`：`capacity` 直接等于固体燃料质量换算单位，乘同一系数。
    """

    part = models.OneToOneField(
        PartCatalog,
        verbose_name='对应部件',
        on_delete=models.CASCADE,  # 1:1 子表随超类消失（基准 4.16）
        related_name='fuel_tank',
    )
    wet_mass = models.FloatField('满载质量', help_text='单位 t。必须 ≥ 对应部件的干重。')
    capacity = models.FloatField('燃料容量', help_text='单位「单位」，LF+OX 合计；1 单位≈0.005 t。')
    fuel_type = models.CharField('燃料类型', max_length=12, choices=FuelType.choices)
    usable_capacity = models.FloatField(
        '可用容量', null=True, blank=True, help_text='单位「单位」。为空表示等于 capacity。'
    )
    is_jet = models.BooleanField('喷气燃料罐', default=False)
    note = models.TextField('备注', blank=True)

    class Meta:
        verbose_name = '燃料罐'
        verbose_name_plural = '燃料罐'
        ordering = ['part__name']
        constraints = [
            models.CheckConstraint(
                condition=models.Q(capacity__gte=0), name='fueltank_capacity_nonneg'
            ),
            models.CheckConstraint(
                condition=models.Q(wet_mass__gte=0), name='fueltank_wet_mass_nonneg'
            ),
        ]

    def __str__(self):
        return f'{self.part.name}（{self.get_fuel_type_display()} {self.capacity:g} 单位）'

    @property
    def effective_capacity(self):
        """实际可用容量：`usable_capacity` 为空时回退到 `capacity`。"""
        return self.capacity if self.usable_capacity is None else self.usable_capacity

    @property
    def fuel_mass(self):
        """满载时燃料质量（t）。系数 0.005 t/单位，与 `core.constants.FUEL_UNIT_MASS` 一致。"""
        return self.effective_capacity * 0.005

    def clean(self):
        super().clean()
        errors = {}
        # ★ 跨表校验：需要读取 part.dry_mass → SQLite 的 CHECK 无法子查询，故放 clean()（见 2.4）
        if self.part_id and self.wet_mass is not None and self.part.dry_mass is not None:
            if self.wet_mass < self.part.dry_mass:
                errors['wet_mass'] = (
                    f'满载质量（{self.wet_mass:g} t）不得小于对应部件干重'
                    f'（{self.part.dry_mass:g} t）。'
                )
        if self.usable_capacity is not None:
            if self.usable_capacity < 0:
                errors['usable_capacity'] = '可用容量不能为负。'
            elif self.capacity is not None and self.usable_capacity > self.capacity:
                errors['usable_capacity'] = '可用容量不得超过总容量。'
        if self.is_jet and self.fuel_type != FuelType.LF_OX:
            errors['fuel_type'] = '喷气燃料罐的燃料类型应为「液体燃料+氧化剂」。'
        if errors:
            raise ValidationError(errors)

"""stages app：级（本项目语境中的「级间段」，决策 D-07）与级-燃料罐挂载。

from core.mixins import TimeStampedModel

```python
# programs/models.py
"""programs app：航天计划（1 端）+ 计划成员链接（n 端）。

★ 决策 D-06：用 `ProgramLink` 链接表 + 可空 FK + CHECK 恰好一个非空，
实现**真 1:n、外键完整、加新对象类型不动老表**。
"""
from django.core.exceptions import ValidationError
from django.db import models

from core.mixins import CodeModel, TimeStampedModel


class ProgramStatus(models.TextChoices):
    """计划状态（基准 4.12）。"""

    PLANNED = 'PLANNED', '规划中'
    ACTIVE = 'ACTIVE', '进行中'
    COMPLETED = 'COMPLETED', '已完成'
    CANCELLED = 'CANCELLED', '已取消'


class ProgramObjectType(models.TextChoices):
    """计划成员类型（基准 4.13）。"""

    CARRIER = 'CARRIER', '火箭'
    PAYLOAD = 'PAYLOAD', '载荷'
    FLIGHT = 'FLIGHT', '发射日志'
    SITE = 'SITE', '发射场'
    SPACECRAFT = 'SPACECRAFT', '航天器'


class Program(TimeStampedModel, CodeModel):
    """航天计划（1:n 的「1」端）。"""

    name = models.CharField('计划名称', max_length=80, unique=True)
    objective = models.TextField('计划目标')
    status = models.CharField(
        '计划状态',
        max_length=12,

        default=ProgramStatus.PLANNED,

    )
    target_body = models.ForeignKey(

        verbose_name='主要目标天体',
        null=True,
        blank=True,
        on_delete=models.SET_NULL,   # 天体删除不应连带删除计划（基准 4.16 的 SET_NULL 一族）
        related_name='programs',
    )
    start_ut = models.FloatField('计划开始', null=True, blank=True, help_text='KSP 游戏时间 UT（秒）。')
    end_ut = models.FloatField('计划结束', null=True, blank=True, help_text='KSP 游戏时间 UT（秒）。')
    budget = models.PositiveIntegerField('预算', null=True, blank=True, help_text='单位 √。')
    spent = models.PositiveIntegerField('已花费', default=0, help_text='单位 √。')
    priority = models.PositiveIntegerField('优先级', default=3, help_text='1 最高，5 最低。')
    description = models.TextField('说明', blank=True)

    class Meta:
        verbose_name = '航天计划'
        verbose_name_plural = '航天计划'

        indexes = [
            models.Index(fields=['status', 'priority'], name='idx_program_status_priority'),

        constraints = [
            models.CheckConstraint(
                condition=models.Q(priority__gte=1) & models.Q(priority__lte=5),
                name='program_priority_range',
            ),

        return f'{self.name}（{self.code}）'

        if None not in (self.start_ut, self.end_ut) and self.end_ut < self.start_ut:
            errors['end_ut'] = '计划结束时间早于计划开始时间。'

            # 超支是玩家常见情形，仅提示不阻断 —— 此处不产生错误，由界面显示警告

            return None

class ProgramLink(models.Model):
    """计划成员链接（1:n 的「n」端，多态挂接）。

    ★ 约束设计（基准 4.13 / 决策 D-06）：
    - CHECK `programlink_exactly_one_object`：`object_type` 与"哪一个 FK 非空"严格对应。
    - 5 条 `UniqueConstraint` 保证「**同一计划内同类型对象不重复**」，
      并由于 `(program, object_type, X)` 中 X 非空，等价于「**一个对象最多归属一个计划**」。
    - ⚠️ SQLite（及 MySQL）中 **NULL 不参与唯一性比较**：一行是"载荷成员"时
      `carrier` 为 NULL，在 `uniq_program_carrier` 眼中不构成键冲突，故 5 条约束互不干扰。
      **切勿把可空 FK 改成 null=False + 哨兵值（如 0），否则唯一性语义立刻互相误伤。**
    - 若将来需要「一个对象参与多个计划」，只需移除这 5 条唯一约束，**表结构无需改动**。
    """

    program = models.ForeignKey(
        Program,
        verbose_name='所属计划',
        on_delete=models.CASCADE,   # 计划删除则成员关系消失（成员对象本身保留）
        related_name='links',
    )
    object_type = models.CharField('成员类型', max_length=12, choices=ProgramObjectType.choices)
    carrier = models.ForeignKey(
        'carriers.CarrierModel', verbose_name='火箭',
        null=True, blank=True, on_delete=models.CASCADE, related_name='program_links',
    )
    payload = models.ForeignKey(
        'payloads.PayloadModel', verbose_name='载荷',
        null=True, blank=True, on_delete=models.CASCADE, related_name='program_links',
    )
    flight = models.ForeignKey(
        'launches.FlightLog', verbose_name='发射日志',
        null=True, blank=True, on_delete=models.CASCADE, related_name='program_links',
    )
    site = models.ForeignKey(
        'sites.Site', verbose_name='发射场',
        null=True, blank=True, on_delete=models.CASCADE, related_name='program_links',
    )
    spacecraft = models.ForeignKey(
        'spacecraft.Spacecraft', verbose_name='在轨航天器',
        null=True, blank=True, on_delete=models.CASCADE, related_name='program_links',
    )
    role_note = models.CharField('在本计划中的角色', max_length=120, blank=True)
    added_at = models.DateTimeField('加入时间', auto_now_add=True)

    class Meta:
        verbose_name = '计划成员'
        verbose_name_plural = '计划成员'
        ordering = ['program', 'object_type', 'id']
        indexes = [
            models.Index(fields=['program', 'object_type'], name='idx_plink_program_type'),
        ]
        constraints = [
            # ★ 恰好一个对象非空，且与 object_type 一致（基准 4.13 原文代码）
            models.CheckConstraint(
                condition=(
                    models.Q(object_type='CARRIER', carrier__isnull=False, payload__isnull=True,
                             flight__isnull=True, site__isnull=True, spacecraft__isnull=True)
                    | models.Q(object_type='PAYLOAD', carrier__isnull=True, payload__isnull=False,
                               flight__isnull=True, site__isnull=True, spacecraft__isnull=True)
                    | models.Q(object_type='FLIGHT', carrier__isnull=True, payload__isnull=True,
                               flight__isnull=False, site__isnull=True, spacecraft__isnull=True)
                    | models.Q(object_type='SITE', carrier__isnull=True, payload__isnull=True,
                               flight__isnull=True, site__isnull=False, spacecraft__isnull=True)
                    | models.Q(object_type='SPACECRAFT', carrier__isnull=True, payload__isnull=True,
                               flight__isnull=True, site__isnull=True, spacecraft__isnull=False)
                ),
                name='programlink_exactly_one_object',
            ),
            models.UniqueConstraint(fields=['program', 'object_type', 'carrier'],
                                    name='uniq_program_carrier'),
            models.UniqueConstraint(fields=['program', 'object_type', 'payload'],
                                    name='uniq_program_payload'),
            models.UniqueConstraint(fields=['program', 'object_type', 'flight'],
                                    name='uniq_program_flight'),
            models.UniqueConstraint(fields=['program', 'object_type', 'site'],
                                    name='uniq_program_site'),
            models.UniqueConstraint(fields=['program', 'object_type', 'spacecraft'],
                                    name='uniq_program_spacecraft'),
        ]

    def __str__(self):
        return f'{self.program.name} ← {self.get_object_type_display()} {self.target_object}'

    @property
    def target_object(self):
        """多态取回被链接的对象。"""
        return getattr(self, self.object_type.lower(), None)

    def clean(self):
        super().clean()
        fk_map = {
            ProgramObjectType.CARRIER: 'carrier',
            ProgramObjectType.PAYLOAD: 'payload',
            ProgramObjectType.FLIGHT: 'flight',
            ProgramObjectType.SITE: 'site',
            ProgramObjectType.SPACECRAFT: 'spacecraft',
        }
        errors = {}
        filled = [
            name for name in fk_map.values()
            if getattr(self, f'{name}_id', None) is not None
        ]
        if len(filled) != 1:
            errors['object_type'] = '必须且只能指定一个成员对象（火箭/载荷/发射日志/发射场/航天器）。'
        elif fk_map.get(self.object_type) != filled[0]:
            errors[fk_map.get(self.object_type, 'object_type')] = (
                f'成员类型为「{self.get_object_type_display()}」时，'
                f'应填写对应字段，但当前填写的是其他对象。'
            )
        if errors:
            raise ValidationError(errors)

        super().clean()
        errors = {}
        # ★ 跨表校验：sma > Body.radius（基准 4.14 明确要求放 clean()）

            if self.sma <= self.body.radius:
                errors['sma'] = (
                    f'半长轴（{self.sma:,.0f} m）必须大于天体半径'
                    f'（{self.body.radius:,.0f} m），否则航天器位于天体内部。'
                )
        if self.eccentricity is not None and not (0 <= self.eccentricity < 1):
            errors['eccentricity'] = 'v1 只处理椭圆轨道，离心率须满足 0 ≤ e < 1（逃逸轨道请用 situation=ESCAPING 记录）。'
        if self.inclination is not None and not (0 <= self.inclination <= 180):
            errors['inclination'] = '轨道倾角必须在 0–180 之间。'
        for field_name, label in (
            ('lan', '升交点经度'), ('arg_pe', '近拱点幅角'),
            ('true_anomaly', '真近点角'), ('mean_anomaly_at_epoch', '历元平近点角'),
        ):
            value = getattr(self, field_name)
            if value is not None and not (0 <= value <= 360):
                errors[field_name] = f'{label}必须在 0–360 之间。'
        if self.altitude is not None and self.altitude < 0:
            errors['altitude'] = '当前高度不能为负（低于地表请改用 situation=LANDED/SPLASHED）。'
        if self.situation in (Situation.ORBITING, Situation.ESCAPING) and self.sma is None:
            errors['sma'] = '状态为「环绕轨道/逃逸中」时应填写半长轴。'
        if self.cached_period_sec is not None and self.sma is None:
            errors['cached_period_sec'] = '未填写半长轴时无法对照周期快照，请先填写半长轴。'
        if errors:
            raise ValidationError(errors)

    # —— 以下仅为便捷访问器；真正的计算在 services/orbital.py（基准 8.7）——
    # 之所以不在此处 import services：保持 models 层零业务计算依赖，便于移植与测试。

    @property
    def has_orbit(self):
        return self.sma is not None and self.body.mu is not None
```

**索引设计原则小结**：

1. **组合索引的列序 = 等值条件在前、范围/排序在后**（`state` + `planned_ut`、`body` + `is_active` + `situation`）。
2. **不为选择性极低的布尔列单独建索引**，而是放进组合索引。
3. **不外建"给我全表排序"的索引**：数据量在千级（第 12 节），SQLite 全表扫可接受。
4. **`series` 类"分组列"建单列索引**，让 `GROUP BY series` 走索引扫描而非临时表。

### 4.3 唯一约束说明（含 `ProgramLink` 5 条约束为何能共存）

#### 4.3.1 `code` 唯一性

- 8 张业务主表（`Body`/`PartCatalog`/`CarrierModel`/`PayloadModel`/`Site`/`FlightLog`/`Program`/`Spacecraft`）以及 3 张部件子表（`FuelTank`/`Engine`/`ScienceInstrument`，基准 4.15 明确"另设 `code`"）各有 `code` 唯一约束。
- 部件子表的 `code` 与 `part.code` **可以不同**：`part.code` 是"部件目录编号"（`PART-*`），子表 `code` 是"专有记录编号"（`TANK-*`/`ENG-*`/`SCI-*`）。界面以 `part.code` 为主键展示，子表 `code` 用于直接引用子表记录（如 06 文档引用具体引擎参数）。

#### 4.3.2 `name` 唯一性

- 除 `FlightLog.name` 外，所有业务表的 `name` 都 `unique=True`（基准字段清单逐条如此）。**`FlightLog.name` 不唯一是有意的**：任务名可能重复（"落日六号验证计划"两次尝试），唯一性由 `code`（`SCP-2026-014`）承担。

#### 4.3.3 `ProgramLink` 的 5 条唯一约束：NULL 为何不冲突

```sql
-- Django 生成的 S 大致形如：
CREATE UNIQUE INDEX uniq_program_carrier    ON programs_programlink (program_id, object_type, carrier_id);
CREATE UNIQUE INDEX uniq_program_payload    ON programs_programlink (program_id, object_type, payload_id);
CREATE UNIQUE INDEX uniq_program_flight     ON programs_programlink (program_id, object_type, flight_id);
CREATE UNIQUE INDEX uniq_program_site       ON programs_programlink (program_id, object_type, site_id);
CREATE UNIQUE INDEX uniq_program_spacecraft ON programs_programlink (program_id, object_type, spacecraft_id);
```

**机制**：SQLite（以及 MySQL、PostgreSQL）的 `UNIQUE` 索引遵循 SQL 标准 —— **`NULL` 与任何值都不相等，包括另一个 `NULL`**。因此：

| 行 | `object_type` | `carrier_id` | `payload_id` | 在 `uniq_program_carrier` 中 | 在 `uniq_program_payload` 中 |
|---|---|---|---|---|---|
| A | `PAYLOAD` | `NULL` | 7 | 键含 NULL → **不参与** | 键 `(1,'PAYLOAD',7)` |
| B | `PAYLOAD` | `NULL` | 9 | 键含 NULL → **不参与** | 键 `(1,'PAYLOAD',9)` → 不冲突 |
| C | `CARRIER` | 3 | `NULL` | 键 `(1,'CARRIER',3)` | 键含 NULL → **不参与** |

于是 5 条约束各自只对自己那一列生效，**互不误伤**，合计实现两个语义：

1. **同一计划内、同类型的同一个对象只能链接一次**（"别把同一枚火箭加两次"）。
2. **一个对象最多归属一个计划**（等价于「1 计划 : n 对象」的强约束，基准 4.13 的基数表述）。

> ⚠️ **设计红线**：一旦把任一可空 FK 改成 `null=False` + 哨兵值（如 `0`），哨兵值会**参与**唯一性比较，5 条约束立刻互相冲突（例如所有"载荷成员"的 `carrier_id=0` 会让 `uniq_program_carrier` 在第二行就报错）。该注意事项已写入模型注释与第 11 节。
>
> 🔁 **可扩展性**：若将来允许"一个对象参与多个计划"，**只需移除这 5 条 `UniqueConstraint`，表结构无需任何改动**（基准 4.13 明确要求写入本文）。

#### 4.3.4 `Stage` 的两条级序号唯一约束同理

`uniq_carrier_stage_order = UNIQUE(carrier_id, stage_order)` 与 `uniq_payload_stage_order = UNIQUE(payload_id, stage_order)`：火箭的级行 `payload_id IS NULL`，故只受前者约束；载荷的级行 `carrier_id IS NULL`，只受后者约束。**同一个 `stage_order` 值可以在"火箭侧"和"载荷侧"各出现一次而互不冲突。**

#### 4.3.5 `StageTank` 的唯一约束是"普通三列唯一"

`uniq_stage_tank_mount = UNIQUE(stage_id, fuel_tank_id, mount_position)` 三列**都非空**（`stage`/`fuel_tank` 无 `null=True`，`mount_position` 有默认值），因此它是**真正的三列联合唯一**：同一级里同型燃料罐在**同一种安装方式下**只能有一行。想要"4 个堆叠 + 2 个径向"是可以的（两行，`mount_position` 不同），这正是设计意图。

## 6. 范式分析与反规范化说明

### 6.1 达到 3NF 的部分

| 分析对象 | 结论 | 依据 |
|---|---|---|
| `PartCatalog` + `FuelTank`/`Engine`/`ScienceInstrument` | **3NF 且消除多值依赖** | 部件的公共属性（`name`/`diameter`/`dry_mass`/`cost`/`tech_node`/`manufacturer`）是**所有部件类型真正共享**的，是货真价实的 1:1 超类；换成单表宽表会引入大量 `NULL`（引擎没有 `capacity`，燃料罐没有 `isp_vac`），换成每类一张全字段表会重复公共属性。基准 2.5 已论证 |
| 族层级（`EngineFamily`/`StageFamily`/`CarrierFamily`/`PayloadFamily`） | **判定为可消除的传递依赖，故取消（决策 D-08）** | 族只携带「名称 + 描述（可继承默认值）」，n 端成员**无共享实质属性**（`AJ10` 的 7 个成员共享的只有 `vac=True`）。族表值得独立存在的唯一条件是"携带 n 端无法共享、非派生、写入会重复的实质属性"——四条都不成立。替换方案：`series` 列（分组）+ `derived_from` 自引用 FK（血缘），**信息更丰富、少一张表、少一个 JOIN** |
| `Stage` + `StageTank` | **3NF** | 级-燃料罐是真正的多对多关系（一级多罐、一罐可用于多级），用链接表 + `quantity` 表达；`ek` 的 `Stage(engine, count)` 思路保留 |
| `Body` 自引用树 | **3NF**（`parent` 是 `id` 的外键，无循环依赖） | 层级不是"重复存储的路径字符串"，而是靠 `parent` 递归得出，不存在传递依赖 |
| `Program` + `ProgramLink` | **3NF** | 计划与成员对象是真 1:n；用判别列 + 可空 FK 的多态而非"5 张链接表"（后者会让"加新对象类型"必须改表） |
| `Spacecraft` 轨道要素 | **3NF** | 只存 6 个独立的轨道要素 + 历元；`period`/`periapsis`/`apoapsis` 是函数依赖，**不落库** |
| `FlightLog` | **3NF** | `state`/`planned_ut`/`actual_ut` 互相独立（"计划时间"与"实际时间"不是派生关系） |

### 6.2 有意的反规范化/简化（逐条论证）

#### ① `FuelTank.capacity` 不做 LF/OX 分账（**完整保留基准 4.3 的论证**）

> **容量语义（基准 4.3，已按 v1.1 更正）**：`capacity` = **燃料资源单位数**。质量换算恒定使用 `FUEL_UNIT_MASS = 0.005 t/单位`（即 **1 单位 = 5 kg**）；基准初稿曾误写「1 单位 ≈ 1 kg」，该表述已删除。
> - `LF_OX`：`capacity` 为 **LF + OX 合计**单位；单位质量按 KSP 混合比折算，统一取 **0.005 t/单位**的**混合平均质量**。
> - **该系数的实证**（已核对）：`(wet_mass − dry_mass) / 0.005 = capacity` 在三个原版燃料罐上精确吻合 —— FL-T800 `(4.5−0.5)/0.005 = 800`、FL-T400 `= 400`、FL-T200 `= 200`。
> - `SOLID`：`capacity` 直接等于固体燃料质量换算单位，乘同一系数。

**为何这是反规范化/简化**：严格建模应有两列（`lf_capacity`/`ox_capacity`）+ 两种密度常数（LF 0.005 t/单位、OX 0.005 t/单位，但混合比 0.9:1.1 会让"每单位混合燃料"的质量略不同于单组分密度）。本设计**把两列合并为一列、用一个混合平均系数近似**。

**理由与影响**：

1. **Δv 计算只需要"总燃料质量"**（基准 8.1：$m_0 = m_{干} + m_{燃料} + m_{上方} + m_{载荷}$），**不需要 LF/OX 配比**。合并后 `fuel_mass = capacity × 0.005` 一步到位。
2. **KSP 1.12 之后 LF/OX 密度统一**（两者都是 5 kg/单位），混合燃料的真实密度与单一系数**一致**，故这不是"精度换简化"，而是"与现代 KSP 数据模型对齐"。RSS 等改密度的模组需要重新采集常数（已记入基准 R-02）。
3. **代价已公示**：基准 R-02 明确"Δv 计算有系统性偏差（量级正确）"，`06-核心计算设计` 必须标注为已知简化。
4. **可逆性**：若将来要分账，只需给 `FuelTank` 增加 `lf_ratio` 之类的列并改 `services/deltav.py`，**不影响其他表**。

**实现落点**：`core/constants.py` 的 `FUEL_UNIT_MASS = 0.005`（基准 9 节），`FuelTank.fuel_mass` 属性与 `services/deltav.stage_fuel_mass()` 共用该常数，**不允许在别处再出现字面量 0.005**。

#### ② `CarrierModel.max_payload_mass` 是玩家声明的设计目标，不是计算值

- **反规范化在哪**：改由 `Stage`+`StageTank`+`Engine`+`FuelTank` 配置后，运力**可以被计算**（基准 8.1/8.2 的逐级 Δv 与 TWR）。再存一个"运力"数值，就有两个来源。
- **为何仍然保留**：这是**设计意图（design intent）**，与"计算出的能力（computed capability）"是**两个不同的事实**，不是同一事实的两份拷贝：
  - 玩家设计时说"我要造一枚能打 20 t 到 LEO 的火箭"——这是**目标**；
  - 计算出来是 17.3 t——这是**当前级配置的实际能力**；
  - 两者不一致恰恰是**最有价值的信息**（说明级配置还没调到位，或设计目标不现实）。
- **与"被移除的字段"的区别**：`Cleo`(LEO 运力) 被移除是因为它**宣称的语义就是计算结果**（"这枚火箭的 LEO 运力"），必然与级配置漂移；`max_payload_mass` 的语义是"设计要求"，**不与计算值构成同一函数的两个副本**。
- **防漂移策略**：界面**并列显示**「设计目标 / 计算值」，偏差超过阈值时给出提示（写入 `05-页面交互设计`）。**禁止**把计算值回写到该字段。

#### ③ `Spacecraft.cached_period_sec` 是可选的玩家抄录快照

- **反规范化在哪**：`period` 是 $a$ 与 $\mu$ 的函数（基准 8.3），独立存储必然漂移（决策 D-12 明确"派生量不落库"）。
- **为何仍然保留**：它是**外部证据**，不是派生值。玩家从 MechJeb/KER 抄下的周期可能与我们的公式结果不同，原因可能是：① KSP 版本差异；② 模组改变 $\mu$；③ 抄录时用的不是同一个 `sma`；④ 公式实现有 bug。**保留抄录值让我们能发现后两种问题。**
- **防漂移策略**：`sma` 是唯一权威输入；界面**并列显示「计算值 / 录入值」**，偏差 >1% 时提示（基准 8.3）；`clean()` 要求"填了快照就必须填 `sma`"（否则无从对照）。
- **可空**：默认 `NULL`。绝大多数航天器不会填。

#### ④ `FlightLog.rest_dv` 是抄录值

- **反规范化在哪**：剩余 Δv 理论上可由"发射时总 Δv − 消耗"推算，但**KSP 里没有任何可靠数据源告诉我们"发射时总 Δv"**。
- **为何保留**：这是**玩家从 KER/MechJeb 读数抄录的观测值**，用于事后复盘（"这枚火箭实际还剩 1000 m/s"）。与 ②③ 同属"抄录快照"模式。
- **类型说明**：基准定为 `IntegerField`（整数 m/s），比 `FloatField` 更省空间、显示更干净；**精度损失可接受**（Δv 读数本身是整数显示）。
- **为何不是"派生值冗余"**：`CarrierModel` 不再存"总 Δv"，故 `rest_dv` 没有可比的"权威输入"，它是**唯一的记录**，不存在两个副本。

> **四处反规范化的共同判据**（可复用的决策规则）：
> **「这个值能否从库内其他字段确定性地重算出来？」**
> - 能，且语义上就是那个计算结果（`Cleo`/`Cmass`/`Cthrust`/`Cratio`/`period`）→ **不落库，实时算**；
> - 不能，或它是**外部观测/玩家意图**（`max_payload_mass`/`cached_period_sec`/`rest_dv`）→ **落库，但与计算值并列展示并标注来源**。

## 7. 被移除的旧字段及其论证

### 7.1 移除清单

旧 `Carrier` 表（`arock.sql:6-18`）共 11 个字段，其中 **5 个被移除 + 1 个语义改造**：

| 旧字段 | 旧类型 | 旧注释 | 处置 |
|---|---|---|---|
| `Cleo` | `FLOAT` | LEO 低地球轨道运力(t) | **移除** |
| `Cgto` | `FLOAT` | GTO 地球同步转移轨道运力(t) | **移除** |
| `Cmass` | `FLOAT` | 箭体质量(t) | **移除** |
| `Cthrust` | `FLOAT` | 最大推力(MN) | **移除** |
| `Cratio` | `FLOAT` | 最小地面推重比 | **移除** |
| `Cconfig` | `VARCHAR(100)` | 各级配置 | **语义扩展**为 `CarrierModel.description`（`TextField`）——旧值是"助推器：RT10,一级：T45+T1000"这种自由文本，新设计的级配置由 `Stage` 表结构化承载，`description` 只留"设计说明" |

### 7.2 移除理由（本设计最实质的数据模型改进之一）

**核心判据**：**这五个字段全部是"从级配置派生"的量。** 有了 `Stage` + `StageTank` + `Engine` + `FuelTank` 之后：

| 被移除的量 | 现在如何得到 | 落点 |
|---|---|---|
| **LEO 运力** | 逐级 Δv 累加 + 目标轨道的 Δv 需求，反解得可送载荷质量 | `services/deltav.vehicle_delta_v()` |
| **GTO 运力** | 同上（换目标轨道 Δv 需求，`06` 给转移轨道 Δv） | `services/deltav.py` |
| **箭体总质量** | `Σ(级干重 + 级燃料质量)`，其中级干重 = `Σ(StageTank 部件干重 × quantity) + Engine.dry_mass × engine_count + decoupler_mass`，级燃料质量 = `Σ(FuelTank.capacity × quantity) × FUEL_UNIT_MASS` | `services/deltav.stage_dry_mass()` / `stage_fuel_mass()`（基准 8.1 已给出公式） |
| **最大推力** | `Engine.thrust_asl × engine_count`（逐级取最大，或取起飞级） | `services/deltav.py` |
| **最小地面推重比** | $F/(m_0 g_{local})$，$g_{local}=\mu/r^2$ | `services/deltav.liftoff_twr()`（基准 8.2） |

**结论（须写入 `07-重构方案`，基准 4.6 原文口径）**：

> 这些是**从级配置派生**的量。在有了 `Stage` + `StageTank` + `Engine` 之后，LEO 运力/总质量/最大推力/推重比都能算出来（见 `06-核心计算设计`），再手工录入一份就是**冗余数据，必然与级配置漂移**。这是本次重构最实质的数据模型改进之一。

**补充论据（本文件新增，供 `07` 引用）**：

1. **旧数据已经在漂移**：`arock.sql:20` 的「星云-1」`Cleo=20, Cgto=5, Cmass=21.685`——`Cmass=21.685 t` 却宣称 `Cleo=20 t` 运力，而 `Cratio=5.28`（地面推重比 5.28 对 21.685 t 箭体意味着 1123 kN 起飞推力）。这三个数之间**没有任何自洽性校验**，改一个不会动另一个。这正是"冗余字段必然漂移"的实证。
2. **单位错误也被固化**：旧注释写 `Cthrust` 为 `MN`（兆牛），而 KSP 惯用 **kN**；`Cno` 的 `'01010'` 之类编号在 KSP 语境下无语义。移除派生字段的同时顺带修正了单位口径（设计原则 P-06）。
3. **旧表根本无法表达"级"**：`Cconfig VARCHAR(100)` 只是"助推器：RT10,一级：T45+T1000"的**自由文本**——既不能 JOIN 到引擎表，也不能算质量。移除外加 5 个"看起来像算过"的数值，等于**用 `Stage` 表把这个能力真正建起来**。
4. **`description` 保留了信息**：旧 `Cconfig` 的文字内容可原样迁入 `CarrierModel.description`（`TextField`，无长度限制），信息不丢失；结构化信息由 `Stage` 表承担。

### 7.3 保留的"运力"类字段

**保留 `CarrierModel.max_payload_mass`（`FloatField`，可空）作为玩家声明的设计目标（设计意图，非计算结果），与计算值在界面上并列显示，不一致时给出提示。**（基准 4.6 原文口径）

- 旧 `Cleo` 的语义是"这枚火箭的 LEO 运力"（**声称是计算值**）→ 移除。
- 新 `max_payload_mass` 的语义是"我设计它时打算送多少吨"（**声明是意图**）→ 保留，并在 `help_text` 中明确标注"设计目标，不是计算值"。

### 7.4 移除的连带收益

| 收益 | 说明 |
|---|---|
| 消灭"假精确" | 界面不再显示"手工录入的运力/推重比"，只显示**基于级配置现算的值 + 声明目标**，两者来源在 UI 上可区分 |
| 与 `Payload.mass` 不再重复 | 旧设计里"运力"与"载荷质量"是两处独立数据，现在运力由公式从级配置推出、载荷质量由 `PayloadModel.mass` 提供，二者在计算中相遇而非在表中重复 |
| 减少录入工作量 | 新增一枚火箭只需录"级 + 引擎 + 燃料罐"，运力/质量/推力/推重比**自动出现** |

## 10. 迁移策略

### 10.1 Django migrations 取代 `arock.sql` 的重建方式

| 维度 | 旧方案（`arock.sql`） | 新方案（Django migrations） |
|---|---|---|
| 建表 | `DROP DATABASE IF EXISTS arockDB; CREATE DATABASE; CREATE TABLE ...` | `makemigrations` 生成 Python 迁移文件 → `migrate` 应用 |
| 改字段 | **手工改 SQL 后重建库，数据全丢** | 生成 `AlterField` 迁移，**原地改列、数据保留**（SQLite 下自动重建表并搬数据） |
| 增字段 | 手工 `ALTER TABLE`（旧项目实际上靠重建） | `AddField` 迁移（如 `null=True` 可直接加列） |
| 版本化 | 无（一个 86 行的 DDL 文件） | 每个迁移文件是**有序、可回滚（`migrate app 0002`）、可审计**的版本节点 |
| 团队协作 | 靠"重新执行 arock.sql" | 迁移文件入库，`migrate` 幂等 |
| 生产变更 | `DROP DATABASE` | 增量迁移，**不删数据** |
| 对应缺陷 | 基准 11.2-⑬「无数据库迁移机制（`DROP DATABASE` 重建）」 | 本次修复 |

**本项目只产出文档不做代码（决策 D-11）**，因此迁移文件在 P0–P4 实施阶段由 `makemigrations` 自动生成；本文件规定**其命名与顺序的预期**，作为 `08-任务清单` 的验收项。

### 10.3 从旧库迁移的三条路线（基准 11.4）

> **⚠️ 本节已按基准 v1.1 更正两次**。初稿依据基准「建议 路线 A」写成；基准随后改为「推荐 路线 B」（因核实 `arock.sql` 发现 KSP 主题内容）；但 `07` 撰写者核实出 **CSV 里有 82 行真实地球航天数据**，其反驳成立。
> **最终：三条路线并列，基准现推荐 路线 C 混合路线，但此项交由用户裁决**（见基准 R-07）。

| 路线 | 做法 | 工作量 | 建议 |
|---|---|---|---|
| **路线 A · 不迁移** | 直接建新库、灌 KSP 种子数据（天体 17 条 + 部件样例） | 0 | 把本项目当**纯 KSP 工具**时适用。代价：旧火箭/载荷/发射记录全部丢失 |
| **路线 B · 全量迁移** | `migrate_legacy.py` 从 `arockdb` 读旧 5 表**全量**映射 | ≈ 1.2 天（含清洗） | 想完整保留旧台账（含 82 行真实地球数据），接受语义混杂 |
| **★ 路线 C · 混合** | 只迁 `arock.sql` 的 17 行（5 火箭 + 3 载荷 + 4 发射场 + 4 日志）；**跳过 CSV 的 82 行** | ≈ 0.5 天 | **基准推荐**：保留 KSP 主题的火箭与级配置，又不污染 KSP 语境 |

**旧数据构成**（完整画像见 `07` §8.2）：`arock.sql` 17 行中火箭带 KSP 部件串（`Cconfig = "助推器：RT10,一级：T45+T1000"`）、日志含 `'kerbin-duna转移轨道_5:50圆轨'`；而 `site_data.csv`(20) / `payload_data.csv`(30) / `scp_data.csv`(30) **几乎全是真实地球航天数据**。

**三条路的共识事实**（无分歧）：**级结构（`Stage`/`StageTank`）在任何路线下都无法自动完整重建** —— `Cconfig` 只是部件串文本，匹配到 `PartCatalog` 必须人工核对。差别在于 路线 B/路线 C 至少有部件串作为解析起点，路线 A 则完全从零录入。

**路线 B/路线 C 的部分自动化现实预期**：`Cconfig` → `Stage`/`StageTank` 可以写成解析器（按 `,` 与 `+` 切分 → 查 `PartCatalog.name` 模糊匹配），但**必须把未匹配项输出为待确认清单**，不能静默猜测。

**若选 路线 B 或 路线 C，脚本必须**：
1. 在 `transaction.atomic()` 中执行，失败整体回滚；
2. 逐行调用 `full_clean()`（因为跨表规则在 `clean()` 里，不在 DB 里）；
3. 输出"未映射值清单"（如遇到 `State='正常'` 到底算 `LAUNCHED` 还是 `PLANNED`，**必须由玩家逐条确认**，不能猜——旧表没有 `planned_ut` 信息）。

## 11. 完整性约束清单

> **等级说明**
> - **DB 级**：由数据库强制（SQLite `CHECK`/`UNIQUE`/`FOREIGN KEY`），任何写入路径都逃不掉，报错为 `IntegrityError`。
> - **`clean()` 级**：由 Django 模型校验强制（`ModelForm`/`full_clean()` 触发），报错为带字段名的 `ValidationError`，可渲染为中文表单错误。
> - **双层**：既写进 DB 兜底，也在 `clean()` 给出友好提示。

### 11.1 CHECK 约束

| # | 表 | 约束名 | 表达式 | 等级 | 原因 |

### 11.4 约束等级统计与设计取向

| 等级 | 数量 | 取向 |
|---|---|---|
| **DB 级**（CHECK + UNIQUE + FK） | 约 70 条 | **凡是 DB 能表达的，一律下推到 DB**（设计原则 P-08） |
| **`clean()` 级** | 9 组 | 跨表引用（2 组）、需中文友好提示（5 组）、启发式质量提示（2 组） |
| **双层** | 3 条 | 不可协商的不变量：DB 兜底 + `clean()` 提示 |

**为什么这个比例是对的**：SQLite 的能力边界（不能子查询、不能 `ALTER` 约束）决定了「跨表规则只能放 `clean()`」；而「友好错误提示」是产品的硬需求（`05-页面交互设计` 的表单错误展示）。**两者的交集恰好就是那 9 组 `clean()` 规则。**

### 12.2 SQLite 完全够用

| 维度 | SQLite 的能力 | 本项目需求 | 余量 |
|---|---|---|---|
| 数据量 | 单库理论上限 **281 TB**；实践中数百万行无压力 | **数千–数万行** | **> 1000×** |
| 单表行数 | 无硬限制（受文件系统与 `rowid` 上限约束） | 最大表 `stages_stagetank` ≈ 1500 行 | 巨大 |
| 单行大小 | 默认页 4096 B，单行 ≤ 页大小（大 `TEXT` 溢出到 overflow page） | 最长字段 `description`/`detail`/`note` 为 `TextField`，数百字节 | 充裕 |
| 数据库文件大小 | — | 估算 **< 5 MB**（数万行 × 数百字节）；即使灌 300 个部件 + 数千发射日志也 **< 20 MB** | 可随电子邮件/网盘轻松拷贝 |
| 查询性能 | 有索引时 `WHERE`+`ORDER BY` 在千行级为**亚毫秒** | 最重的查询是"发射日程"（`state + planned_ut` 组合索引）与"计划总览"（`program + object_type` 组合索引） | 无需任何优化 |
| 索引数 | 每表索引数无实际限制（写放大轻微） | 33 条索引（4.1 节） | 无问题 |
| 并发 | 单写者（库级写锁） | **单人单机自用**，写入间隔以秒计 | 无冲突 |
| 备份 | **拷贝 `db.sqlite3` 一个文件** | 完美契合"游戏记录本"形态 | ★ 这是选型的核心理由之一 |
| 全文检索 | `FTS5` 扩展可用（不改 schema 也能用虚拟表） | v1 不需要（`LIKE` 足够） | 留作扩展 |

### 12.3 性能相关的设计取舍（基于上述评估）

| 取舍 | 理由 |
|---|---|
| **不加缓存层、不做查询优化** | 千行级数据上，`select_related`/`prefetch_related` 已经足够，无需 `Redis`/`django-cachalot` |
| **派生量实时算（决策 D-12）** | 一枚火箭的 Δv 计算是 3–5 级的循环，微秒级；缓存反而引入失效问题（第 6.3 节） |
| **索引只建清单里的 33 条** | 每多一个索引，`loaddata` 灌 300 个部件时就多一次写放大。字段级 `db_index` 只加在真正过滤/排序的列上 |
| **不分区、不分表** | 数千行无需分区 |
| **`PRAGMA journal_mode=WAL` 可选** | 单写者场景收益有限；若玩家一边跑 `runserver` 一边用 Admin 批量录入可开启（见 3.10 代码注释） |
| **不做归档策略** | 数千条发射日志全留，正是"任务记录本"的价值 |

### 12.4 何时需要重新评估选型

保守估计，出现以下任一情形时应回到第 2.2 节评估换 MySQL：

1. 单表行数超过 **100 万**（本项目不可能，除非做存档自动解析且每次物理帧都记一行）；
2. 需要**多用户并发写入**（v1 明确排除，基准 D-09）；
3. 需要**全文检索 + 复杂聚合**（如"在所有任务详情里搜索"），且数据量过万；
4. 需要**跨机器共享**（SQLite 文件放网盘会损坏，应换 C/S 数据库）。

**结论：SQLite（单文件 `db.sqlite3`）在本项目的全部预期数据量下完全够用，且"单文件可拷贝备份"的形态与本工具"游戏记录本"的定位高度契合。**

### 13.3 需要用户确认的点

| # | 待确认项 | 备选 | 本文件的暂定选择 |
|---|---|---|---|
| C-01 | **`FlightLog.rest_dv` 是否允许 NULL** | ① 保持基准的 `IntegerField(null=True)`（NULL = 未记录）② 改为 `default=0`（0 = 未记录） | ①（可空）——因为"零剩余 Δv"与"未记录"必须可区分；本文件已配 `CHECK rest_dv IS NULL OR >= 0` |
| C-02 | **`FlightLog` 状态-时间一致性是否要 DB CHECK 兜底** | ① 仅 `clean()`（基准原文）② `clean()` + 2 条 DB CHECK | ②（双层）——DB 能挡住的脏数据不应只靠 Python；若你希望保持"唯一真源在 `clean()`"，可删去两条 DB CHECK，**表结构不变** |
| C-03 | **`Site.body` 是否可空** | ① 必填（`null=False`）② 可空 | ①（必填）——基准 4.10 未写 `null`，且"发射场必在某天体上"是硬语义；**旧数据迁移需统一填 Kerbin**（基准 11.1 已如此规定） |
| C-04 | **`Program.objective` 是否必填** | ① 必填（基准字段表无 `blank`）② `blank=True` | ①（必填）——按基准字面落实；若觉得"新建计划时还没想好目标"不便，可改 `blank=True`（**属字段级变更，需先回改基准**） |
| C-05 | **`Body.depth` 的计算方式** | ① Python 属性遍历 `parent` 链（本文件）② 递归 CTE（`raw` SQL）③ 加 `depth_hint` 字段 | ①——17 行数据、层级 3 层，Python 遍历零成本；③ 会引入需同步维护的冗余列 |
| C-06 | **`Stage.stage_order` 的方向约定** | ① 1 = 起飞级（最下面一级），向上递增（本文件）② 1 = 最上面一级 | ①——基准 8.1 的"$m_0$ = 本级初始质量 + **上方所有级质量**"暗示计算从下往上累加；`ek` 的 `LV(*stages)` 参数顺序也是从下往上。**此项必须在 `06` 与 `05` 中与页面渲染顺序对齐** |
| C-07 | **`solar_day` 的派生公式** | ① `sidereal_day × 1.002340271`（Kerbin 精确 21600，本文件）② 精确公式 $T_{solar} = T_{sid}/\|1 - T_{sid}/T_{year}\|$（需各天体公转周期） | ①——基准未提供公转周期，无法用②；①对显示层足够，且 Kerbin 值精确。**若你手头有各天体公转周期，可改②**（属种子数据变更，不动模型） |
