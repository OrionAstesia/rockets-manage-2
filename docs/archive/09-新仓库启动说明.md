## 1. 这个仓库是什么

它是 **`F:\Codes\Py_Programs\rocket_manage`**（GitHub: `OrionAstesia/rockets-manage`）的**重构继任者**。

| | 原型仓库（已归档） | 本仓库 |
|---|---|---|
| 技术栈 | Flask + PyMySQL + WTForms + MySQL | **Django 5.2 + SQLite** |
| 领域 | 真实航天运载火箭发射管理（`Carrier`/`Payload`/`Site`/`SCP`） | **KSP 玩法**：部件库 + 级结构 + 发射计划 + 在轨航天器 |
| 表 | 5 张（2 张业务可算） | **14 张，分 9 个 app** |
| 路由 | 22 个 `@app.route` 集中在一个 992 行的 `manage.py` | 50 条路由，按 app 拆分 + `services/` 计算层 |
| 代码位置 | `F:\Codes\Py_Programs\rocket_manage` | `F:\Codes\Py_Programs\rockets-manage-2`（即本仓库） |

## 3. 开工前必须知道的 6 件事

### 3.1 环境：必须用 conda 环境 `rocket`，不能用 PATH 上的 python

本机 PATH 上的 `python` 是 **`D:\MinGW\bin\python.exe`（没有 Django）**。这是一个已经踩过的坑（原型项目也有同类问题）。

```powershell
conda create -n rocket python=3.10 -y
conda activate rocket
pip install "Django==5.2.*" "numpy>=1.26"
python -c "import django; print(django.get_version())"   # 必须输出 5.2.x
```

补充事实：
- 本机 **`conda` 不在 PATH** 中，可执行文件在 `F:\Anaconda\Scripts\conda.exe` 与 `F:\Anaconda\condabin\conda.bat`。必要时用全路径，或直接在 Anaconda Prompt 里操作。
- 现有 `OrionDB` 环境是 **Python 3.9.21** 且**缺 sqlalchemy**，不适合直接用；`rag` 环境是 Python 3.10.19 且已有 django 5.2.17 / numpy 2.2.5，可作版本参照，但**不要污染它**（它服务另一个 RAG 项目）。
- 本机 MySQL 8.4.4 服务在运行，但 **v1 不用**。

### 3.2 数据模型：`03-数据库设计.md` 是冻结的

- 14 张表分 9 个 app：`core`(Body) / `parts`(4) / `carriers`(1) / `payloads`(1) / `stages`(2) / `sites`(1) / `launches`(1) / `programs`(2) / `spacecraft`(1)。
- **⚠️ 是 9 个 app，不是 7 个** —— 文档早期草稿写过「7 个 app」，已在基准 v1.1 修正。若在任何地方看到 7，那是旧值。
- 所有字段名、类型、枚举值、约束名、`on_delete` 策略都以 `03` 为准。**若要改字段，先改 `docs/_design-brief.md` 再同步 `03`**，否则文档之间会互相矛盾。

### 3.3 最易出错的三个技术点

| # | 事项 | 正确做法 |
|---|---|---|
| 1 | **级序方向** | `stage_order=1` = 最先点火的最下面一级；页面**降序**自上而下渲染；Δv 从 `stage_order=1` **升序**累加（算第 1 级时计入**上方所有级 + 载荷**质量）。三处方向不一致是本项目最易弄反的地方 |
| 2 | **`sma` 不等于高度** | `sma` 是轨道半长轴，高度 = `sma − Body.radius`（Kerbin 为 600 km）。基线文档初稿曾把两者混淆，导致算例错了一倍 |
| 3 | **多态 FK 不用 GenericForeignKey** | `Stage` 用 `owner_type` + 双可空 FK + CHECK；`ProgramLink` 同理。Django 的 `GenericForeignKey`/`GenericTabularInline` 依赖 ContentType，**无法建立数据库级外键与 CHECK，且 Admin 内联会绕过约束** |

### 3.5 原型数据：默认不迁移

本仓库是全新实现，**不需要也不建议迁移原型数据**（路线 A）：

- 原型数据是混合体 —— `arock.sql` 的 17 行含 KSP 主题内容（如 `Cconfig = "助推器：RT10,一级：T45+T1000"`），但三个 CSV 的 82 行是**真实地球航天数据**（地球发射场、嫦娥IV/悟空II 等中国航天器名）。
- 全量迁移会造出「Kerbin 上的酒泉卫星发射中心」这类语义错误。
- 若日后确实想保留那 5 枚含 KSP 级配置的火箭，走**路线 C**（只迁 `arock.sql` 的 17 行）——详见基准 §11.4 与 `07` §8。

### 3.6 `07` 里的旧代码引用指向原型仓库

`07-重构方案与实施计划.md` 大量引用旧代码的**文件路径与行号**（如 `manage.py:28`、`forms.py:15`、`mysql_util.py` 的 `finally: self.db.close()`）。这些文件**不在本仓库**，在已归档的原型仓库 `F:\Codes\Py_Programs\rocket_manage`。阅读 `07` 时请建立这个映射。

`07` 中的以下章节属于**历史记录/设计由来**，不是本仓库的开工清单：

## 4. 建议的接手流程

```
1. 读 docs/README.md            → 建立全局认知与阅读顺序
2. 读 docs/01-需求规格说明.md     → 明确要做什么、v1 不做什么
3. 读 docs/02-概念模型.md         → 建立领域概念与关系
4. 通读 docs/03-数据库设计.md     → 数据模型（重点：第 4 节的 Django 模型代码）
5. 按需查阅 04 / 05 / 06          → 接口 / 页面 / 计算
6. 打开 docs/08-任务清单.md       → 从 P0 开始逐项勾选
```

**P0 地基的交付目标**（`08` 的 P0 阶段，约 21 项任务）：
- conda 环境 `rocket` + `requirements.txt` + `.gitignore`
- `config/` 项目骨架（`settings` 拆 base/dev/prod），`SECRET_KEY` 从环境变量读
- 9 个 app 目录
- `core/mixins.py`（`CodeModel` / `TimeStampedModel`）、`core/constants.py`（`G0` / `FUEL_UNIT_MASS` / `KERBIN_DAY`）
- `core/models.py::Body` + `fixtures/bodies.json`（17 个天体）
- `services/orbital.py` + 单元测试

**P0 验收门槛**：`manage.py runserver` 可启动；`/admin/` 可登录；`Body` 17 条种子数据可见；`manage.py test` 全绿。

> **建议第一件事**：写 `services/orbital.py` 并让它的测试通过。它是纯函数、无 Django 依赖、有明确的断言值（`06` §12 与基准 §9.2 已给出实测值），是最快能确认「环境装对了 + 公式写对了」的一步。其中**同步轨道自洽性测试**（对每个天体，`orbital_period(a_sync(mu, sidereal_day), mu) ≈ sidereal_day`）不存在物理量混用的空间，是最可靠的基准测试。

## 5. 与原型仓库的对照速查

| 原型 | 本仓库 |
