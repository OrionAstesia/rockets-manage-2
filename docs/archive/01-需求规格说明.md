## 2. 项目背景与现状

### 2.1 旧系统是什么

**OrionDBTest —— 火箭发射管理系统**，一个基于 Flask 的课程形制 CRUD 应用：

| 项 | 现状 |
|---|---|
| 框架 | Flask（无应用工厂、无蓝图） |
| 入口 | `manage.py`，**992 行单文件，内含全部 26 个路由** |
| 数据库 | MySQL，库名 `arockdb`，**裸 SQL 字符串拼接**，由 `mysql_util.py`（96 行）封装 |
| 建表 | `arock.sql` 手工脚本，**无迁移机制**，靠 `DROP DATABASE` 重建 |
| 表单 | `forms.py`（255 行 / 5 个 WTForms Form） |
| 模板 | 20 个 Jinja2 模板，Bootstrap 3 布局 |
| 认证 | 自写 `register/login/logout` + `passlib.sha256_crypt` + Flask Session |
| 测试 | **无** |
| 数据 | 5 张表 + `users`：`Carrier` / `Payload` / `Site` / `SCP`，配 4 个随机数据生成器与 CSV/SQL 批量数据 |

`README.md` 目前描述的**仍然是这套旧系统**：它把项目介绍为「基于 Flask 框架构建的航天运载火箭发射管理系统」，技术栈写的是 Flask + PyMySQL + WTForms + Passlib SHA-256 + Bootstrap 3 + Jinja2，启动方式为 `python manage.py` 后访问 `http://127.0.0.1:5000`，数据库章节逐字段列出 `Carrier`/`Payload`/`Site`/`SCP`/`users` 五张旧表。

也就是说：**README 与本次重构后的项目定位已经完全脱节，必须随重构一并重写**（新 README 面向玩家用户，见 brief 第 0 节开头「玩家用户阅读 `docs/README.md` 即可」）。

### 2.2 旧系统的实际缺陷（重构的实质理由）

以下缺陷均已在旧代码中核对确认，编号沿用 brief 第 11.2 节的修复清单：

| # | 缺陷 | 证据 |
|---|---|---|
| 1 | 首页 `index()` 查询 `SCPForUser` 视图，但 `arock.sql` **从未创建该视图** → 按 README 初始化后首页必崩 | `manage.py:28` vs `arock.sql`（全文仅 5 个 `CREATE TABLE` + `CREATE DATABASE`，无 `CREATE VIEW`） |
| 2 | `forms.py` 定义了 `LaunchSiteForm`，但 `manage.py:15` **只导入 4 个 Form**，发射场模块用 `request.form.get()` 裸取值、零校验 | `manage.py:15`、`manage.py:459` 起 |
| 3 | 全项目 SQL 字符串拼接，登录处 `WHERE username = '%s'` → **SQL 注入** | `manage.py:908`、`manage.py:74`、`manage.py:613` 等 |
| 4 | `app.secret_key = "secret123"` 硬编码，且写在 `if __name__ == "__main__":` 内 | `manage.py:991` |
| 5 | `app.run(debug=True)` 无环境区分 | `manage.py:992` |
| 6 | 删除走 **GET** `/delete_xxx/<id>`，无 CSRF → 可被跨站触发 | `manage.py:235`、`404`、`563`、`848` |
| 9 | 经纬度 `Slatitude/Slongitude` 为 `CHAR(6)`，**存不下负号 + 小数** | `arock.sql:45-46` 存的是 `'40.00N'` 这类字符串，与 `FloatField` 语义冲突 |
| 10 | `forms.py` 用 `Length(min=6, max=6)` 校验 `Cno`，而 `arock.sql` 是 `CHAR(5)` → **自相矛盾，校验永远不可能通过** | `forms.py:29` vs `arock.sql:7` |
| 11 | 表名 `SCP`、字段 `SCPno/SCPname/SCPdate` 在 KSP 语境下完全无语义 | `arock.sql:55-72` |
| 13 | 无数据库迁移机制、无异常传播（裸 `except` 只写 `log.txt`） | brief 第 11.2 节第 8、13 条 |

**结论**：旧系统的价值在于它已经跑通了一套「多表 + 外键 + CRUD + 认证」的骨架；但它的**业务语义（地球轨道运载火箭）与数据模型（无部件、无级、无轨道、无计划）都不适配 KSP**，因此本项目的性质是**重构**，而非在旧代码上续写。

### 2.3 现在要变成什么（项目定位）

> **定位（引自 brief 第 0.1 节，原话）**：
>
> 《坎巴拉太空计划》（Kerbal Space Program，KSP）玩家的**发射计划与任务记录管理工具**。单机、自用、单人。

技术栈同步替换：**Flask + MySQL + 裸 SQL → Django 5.2 + SQLite + ORM**（决策 D-02 / D-03）。交付物为 8 份重构文档 + 基准文档（决策 D-11），本轮**只产出文档，不写任何 Django 代码**。

## 3. ★ 技术选型论证

> 本章是本文件最重要的章节。它不是「我们选了 Django」一句话，而是**一次真实发生过的方案比较**的完整记录：用户最初的倾向、技术顾问的推荐、被评估过的 5 条路线、六维评分、以及唯一能让争论收敛的那个问题（项目定位）。

### 3.1 起点：用户最初的选择

用户最初的方案是 **① Flask + SQLAlchemy + MySQL**。

理由很直接：**用户熟悉 Flask**。旧系统就是 Flask 写的，自己写过 992 行路由、5 个表单、20 个模板，对「路由函数 + 模板渲染 + 表单校验」这套心智模型已经形成肌肉记忆。换一个 Web 框架意味着重新学一套「怎么做增删改查」的写法。

这是一个**完全合理**的起点：在自用工具场景下，熟悉度直接换算成「多久能用上」。

同时，改用 SQLAlchemy 也是明确的改进意图 —— 旧系统最大的技术债就是裸 SQL 字符串拼接（缺陷 #3 SQL 注入、缺陷 #7 `MysqlUtil` 到处重复实例化），SQLAlchemy 的 ORM 能一次性消灭这两项。

### 3.2 技术顾问（我）最初的推荐

我最初推荐的是 **③ Django 5.2 + SQLite**，核心理由只有一条：

> **Django Admin 白送 14 张表的 CRUD，能砍掉约 70% 的工作量。**

这不是修辞。本项目的实体清单是 14 张表 / 9 个 app（brief 第 3 节），其中：

- `Body`、`PartCatalog`、`FuelTank`、`Engine`、`ScienceInstrument`、`CarrierModel`、`PayloadModel`、`Site`、`FlightLog`、`Program`、`Spacecraft` —— **11 张表是标准 CRUD**，Django Admin 只要写十几行 `admin.py` 就得到一个可筛选、可搜索、可排序、可内联编辑、带权限的后台。
- 在 Flask 路线下，这 11 张表意味着 **11 套「列表 + 新增 + 编辑 + 删除」= 44 个视图函数 + 44 个模板**，这是旧系统 `manage.py` 膨胀到 992 行的根本原因。

次要理由：

- Django ORM 与 migrations 直接消灭旧缺陷 #3（SQL 注入）、#7（连接管理）、#13（无迁移）。
- Django 内置 `auth` 直接消灭旧缺陷「自写登录 + 弱密码哈希」，且内置 PBKDF2 比 `sha256_crypt` 更安全。
- SQLite 单文件 `db.sqlite3` 可整体拷贝备份 —— 与「游戏记录本」这一使用形态天然吻合。

### 3.3 被评估的 5 条路线

评估刻意覆盖了从「最保守」到「最激进」的整个谱系：

| 路线 | 技术栈 | 一句话定位 |
|---|---|---|
| **①** | Flask + SQLAlchemy + MySQL | 保守：只把裸 SQL 换成 ORM，其余不动 |
| **②** | FastAPI + SQLAlchemy + Jinja2 | 折中：享受类型校验与自动文档，同时保留服务端渲染 |
| **③** | **Django 5.2 + SQLite** | 换框架：用 Admin 与 ORM 换掉大部分 CRUD 工作量 |
| **④** | Next.js 全栈 + Prisma + TypeScript | 激进：UI 体验最好，但整体换语言与换工具链 |
| **⑤** | Node/Express + Prisma + htmx | 半激进：换后端语言，UI 仍走服务端渲染 |

### 3.4 六维评分

评分口径：每维 **1–5 分，等权，满分 30**。其中「学习/返工风险」为**反向维度已折算**——分值越高代表**风险越低**（越省心），以保证「总分越高越好」的统一读法。

| 路线 | 开发速度 | 动态表单 UI | 树 + 序关系 | 换库到 PG 零改动 | 物理计算 | 学习/返工风险 | **总分** |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| ① Flask + SQLAlchemy + MySQL | 3 | 3 | 2 | 4 | **5** | **5** | **22** |
| ② FastAPI + SQLAlchemy + Jinja2 | 3 | 3 | 2 | **5** | **5** | 4 | **22** |
| **③ Django 5.2 + SQLite** | **5** | 4 | **4** | 4 | **5** | 4 | **26** |
| ④ Next.js 全栈 + Prisma + TS | 2 | **5** | 4 | 3 | 1 | 1 | **16** |
| ⑤ Node/Express + Prisma + htmx | 3 | 4 | 3 | 4 | 1 | 3 | **18** |

各维度说明：

- **开发速度**：CRUD 屏幕的净人力。③ 因 Admin 直取 5 分；④ 不但没有脚手架，还要同时写 API 层与组件层，故 2 分。
- **动态表单 UI**：本项目最难的交互是「一枚火箭含 n 个级、一个级含 n 个燃料罐」的**嵌套动态表单**（brief 第 7.1 节）。④ 的 React 状态管理最擅长此类增删排序，5 分；① 要手写全部 DOM 操作，2~3 分。
- **树 + 序关系**：「天体自引用树（`Body.parent`）」与「级的有序性（`stage_order` 位置敏感，brief 第 4.8 节）」两件事。Django 的自引用 FK + `UniqueConstraint` + FormSet 排序支持较成熟，4 分；Flask/FastAPI 要自己写递归与排序，2 分。
- **换库到 PG 零改动**：SQLAlchemy 与 Prisma 的方言抽象最好（4~5 分）；Django ORM 换库同样只改 `DATABASES`，但需回归测试 SQLite 特有行为，4 分。
- **物理计算**：Δv、推重比、轨道周期全部是 Python 数值计算（`06-核心计算设计`，含 8 项已实测验算的断言值）。Python 路线直接复用，5 分；Node 路线必须把公式**逐条翻译成 TypeScript**，1 分。
- **学习/返工风险**：① 是用户最熟的技术栈，风险最低（5 分）；④ 引入 TypeScript + Node 工具链 + 前后端边界重构，返工面最大（1 分）。

### 3.5 两条关键洞察

#### 洞察一：④ 路线 UI 最好，但总分最低

④ 在「动态表单 UI」一维拿了唯一的满分 5，这正是本项目交互难点所在 —— 看起来它应该赢。但它总分 **16 分，全场最低**，原因是：

1. **物理计算要从 Python 翻译成 TS（5 分 → 1 分）**。brief 第 9.2 节已经用 Python 实测验证了 8 组验算值（Kerbin 同步轨道半长轴 `a_sync ≈ 3 463 331 m`、回代周期偏差 0.0000%、单级 Δv `3100.1 m/s`、起飞推重比 `2.039` 等），这些是可直接作为单元测试断言的资产。换语言意味着**这些验证全部作废并需要在新语言里重做一遍**，而且新实现与旧验证值之间还多了一层「翻译是否正确」的不确定性。
2. **引入 Node 工具链**。`package.json`、构建、依赖升级、ESM/CJS、TypeScript 配置……对单机自用工具而言，这些全是**不产生任何业务价值的维护成本**。
3. **返工风险最大**。项目定位是「自用工具」，意味着需求会持续变动（玩家玩到哪写到哪）。在需求最不稳定的阶段选择了最重的技术栈，是典型的**用确定性成本去对赌不确定需求**。

> **结论**：④ 是「UI 得分最高的方案」，也是「总分最低的方案」。**单项最优不等于整体最优** —— 一条路线在它最擅长的那一维上的优势，不足以抵消它在其余五维上的劣势。

#### 洞察二：② FastAPI 相对 ① 只多赚极少收益

② 相对 ① 确实有增益，且增益是真实的：**自动 OpenAPI 文档**与 **Pydantic 类型校验**。但这两项增益在本项目里**几乎没有落点**：

- 本项目的形态是**服务端渲染的多页 CRUD**（Django 模板 + Bootstrap 5 + 原生 JS，决策 D-13，**无构建链**），不是前后端分离的 SPA。
- **没有前端消费方**，OpenAPI 文档就只是一份没人看的 JSON；**请求体不是 JSON**，而是 HTML 表单 POST，Pydantic 的请求校验能力用不上（HTML 表单的校验归表单层，不归 API schema）。
- 更真实的是成本侧：FastAPI 的模板/表单内建支持比 Flask 更薄，做「嵌套动态表单」要写的东西**反而比 ① 更多**。

因此 ② 的六维总分与 ① **持平（22 : 22）**：它在类型安全与文档上多赚了一点，又在模板与表单配套上倒赔了一点。**② 是一个好框架，但不是一个适合本项目的框架。**

### 3.6 定位澄清：这个争论只有在回答了「项目是什么」之后才有答案

评估到这一步，出现了僵局：① 与 ② 在「熟悉度」上占优，③ 在「工作量」上占优，谁也说服不了谁。**僵局的根源不是技术，而是评价维度本身没有确定。**

关键洞察是：

> **技术栈之争，只有在先确定「项目是课程设计还是自用工具」之后才有答案 —— 而且两种定位下的结论是相反的。**

| 评价视角 | 有效维度 | 最优路线 | 理由 |
|---|---|---|---|
| **若定位 = 课程设计 / 作业** | 数据库设计规范性、SQL 与关系代数的显式体现、技术栈广度、可展示的「我做了什么」 | **① Flask + SQLAlchemy + MySQL**（或保留裸 SQL 的 Flask + MySQL） | 课程评分看的是**你亲手写出的建表语句、视图、外键、三范式推导与手写 SQL**。Django 的 ORM/Admin/migrations 会把这些**「替你做完」**，反而让工作量与设计能力**不可见**；而 MySQL 通常还是课程的硬性要求。此时「少写代码」是**减分项**。 |
| **若定位 = 自用工具** | 多久能用上、改需求有多痛、维护成本、能否长期跑下去 | **③ Django 5.2 + SQLite** | 玩家不需要向任何人证明自己写了多少行 SQL；需要的是**下个周末就能开始记录发射**，以及**三年后想加一个字段时不用重写四个视图**。此时「少写 70% 的 CRUD 代码」是**决定性优势**。 |

同一个技术问题，两种定位下答案相反。**这也解释了为什么此前所有关于「Flask 好还是 Django 好」的争论都无法收敛：争论的双方在回答不同的问题。**

### 3.7 用户确认与最终选择

用户确认：

- **项目定位 = 自用工具**（决策 **D-01**）。
- 据此**改选路线 ③：Django 5.2 + SQLite**（决策 **D-02 / D-03**）。
- 用户的理由原话是：**「想少写 70% 的 CRUD 代码」**。

选型收敛后，其余决策顺势确定：

| 编号 | 决策 | 结论 |
|---|---|---|
| D-01 | 项目定位 | **自用工具** |
| D-02 | 技术栈 | **Django 5.2 + SQLite** |
| D-03 | 数据库 | **SQLite（`db.sqlite3`）** |
| D-04 | Python 环境 | **新建 conda 环境 `rocket`，Python 3.10** |
| D-13 | 前端 | **Django 模板 + Bootstrap 5 + 原生 JS（无构建链）** |

### 3.8 环境事实（选型时的实测情况）

选型是在以下真实环境上做出的判断，不是纸面推演：

| 项 | 实测情况 | 对选型的影响 |
|---|---|---|
| MySQL | 本机 **MySQL 8.4.4 正在运行**，旧库 `arockdb` 存在 | ① 路线在数据库层面**完全可行**，排除 ① 的理由不是「没有 MySQL」 |
| Node.js | 本机 **Node v24 可用** | ④ / ⑤ 路线**技术上可行**，排除它们的理由是**返工风险与工具链成本**，不是环境缺失 |
| `OrionDB` conda 环境 | **Python 3.9.21，且未安装 sqlalchemy** | **不可直接复用**。旧项目本身不需要 sqlalchemy（它是 PyMySQL 裸 SQL），但 ①/② 路线必须要；加上 3.9 低于 Django 5.2 的最低要求，因此**环境必须重建** |
| 新建 conda 环境 | **`rocket`，Python 3.10**（D-04） | 与 `rag` 环境隔离，避免污染服务 RAG 项目的环境 |
| `rag` conda 环境 | **已安装 Django 5.2 与 numpy** | 作为**版本参照**：说明 Django 5.2 在本机可用，`requirements.txt` 的 `Django==5.2.*` / `numpy>=1.26` 有现成的版本基线 |
| PATH 上的 `python` | 指向 `D:\MinGW\bin\python.exe`，**无 Django** | 运行前**必须 `conda activate rocket`**，这是旧项目也存在的环境陷阱（brief 第 10.2 节） |

### 3.9 换库后路（SQLite → MySQL）

选择 SQLite 不等于放弃 MySQL。**保留的后路是可验证的**：

- **切换成本**：在 Django 下把 `DATABASES` 从 `django.db.backends.sqlite3` 改为 `django.db.backends.mysql`，安装驱动，重跑 `migrate`——**约 1 小时**（决策 D-03）。
- **真正的成本在数据**：已有数据要迁移必须走 `dumpdata` / `loaddata`，且需处理 SQLite 与 MySQL 在类型、约束、`NULL` 唯一性语义上的差异。
- **v1 明确不做**（D-03）。理由：v1 的数据量小（个人记录本量级）、单机单用户、SQLite 完全够用；提前引入 MySQL 只增加部署与备份成本，不换来任何收益。
- **可移植性是通过 ORM 保证的**：本项目**不写任何裸 SQL**（NFR-PORT-03），因此换方言时业务代码零改动。

## 5. 业务目标与核心诉求

### 5.1 四项核心诉求

> **引自 brief 第 0.1 节，按优先级排序**（原文照录）。

### 5.2 从诉求到需求的推导关系

```
诉求 1 记录  ──► 部件库（燃料罐/引擎/科学设备）→ 火箭/载荷/发射场 → 发射日志

诉求 4 在轨  ──► Spacecraft + 轨道要素 + 派生周期
        │
        └──► 六项新增需求：① 燃料罐表 ② 引擎表 ③ 科学设备表
                            ④ 在轨航天器 ⑤ 航天计划 1:n ⑥ 级结构
```

### 5.3 成功的定义

v1 交付成功的判据（即 brief 第 13 节 P0–P4 各阶段验收标准的汇总）：

1. 能建一枚**含 ≥3 级、每级挂 ≥2 种燃料罐**的火箭，详情页显示**逐级 Δv 累加与起飞 TWR**。
2. 「**安排 → 发射 → 记录**」闭环可用：创建计划中的任务 → 在发射日程页看到它 → 一键执行后状态变为已发射并记下 `actual_ut`。
3. 计划总览能**按 `object_type` 聚合**展示全部成员对象。
4. 航天器录入后**实时显示周期与近/远拱点**。
5. 域计算模块（`services/`）单元测试通过，含 Kerbin 同步轨道自洽性验算。

### 6.11 ★ 六项新增需求验收细则

本节把用户提出的 6 项新增需求逐一展开为「**给定…当…则…**」形式的可验收判据。这是本次重构相对旧系统**新增的全部业务能力**。

#### ① 燃料罐表（`parts.FuelTank`）→ FR-PARTS-02

**落点**：`parts_fueltank`（1:1 `PartCatalog`）｜ **须支持的枚举**：`FuelType` = `LF_OX` / `MONO` / `XENON` / `SOLID` / `ORE` / `OTHER` ｜ 字段定义见 `03`（brief §4.3）

**验收标准**：

1. **给定** 一个燃料罐部件，**当** 录入 `wet_mass = 4.5 t` 且其 `part.dry_mass = 0.5 t`，**则** 保存成功。
2. **给定** `wet_mass = 0.3 t` 而 `part.dry_mass = 0.5 t`，**当** 提交，**则** `clean()` 报错「湿重不得小于干重」。**注意**：该校验**必须是模型 `clean()`**，不能做成跨表 `CheckConstraint`——因为跨表 CHECK 在 SQLite 上无 FK 子查询支持（brief §4.3）。
3. **给定** `capacity = -1`，**当** 写入，**则** 被 `fueltank_capacity_nonneg` 数据库级 CHECK 拒绝。
4. **给定** 一个 `LF_OX` 燃料罐 `capacity = 800`，**当** 参与 Δv 计算，**则** 其燃料质量按 **`FUEL_UNIT_MASS = 0.005 t/单位`** 折算为 `4.0 t`（不做 LF/OX 分账）。
5. **给定** `fuel_type` 取值不在枚举内，**当** 保存，**则** 表单拒绝。

#### ② 引擎表（`parts.Engine`）→ FR-PARTS-03

**落点**：`parts_engine`（1:1 `PartCatalog`）｜ **须支持的枚举**：`EngineCycle` = `GAS_GENERATOR` / `STAGED_COMBUSTION` / `EXPANDER` / `PRESSURE_FED` / `SOLID` / `JET` / `NUCLEAR` / `MONO` / `OTHER`；`FuelType` 同① ｜ 字段定义见 `03`（brief §4.4）

**验收标准**：

1. **给定** `thrust_asl = 200`、`thrust_vac = 240`，**当** 保存，**则** 成功；**给定** `thrust_vac = 180 < thrust_asl`，**当** 提交，**则** `clean()` 报错。
2. **给定** `thrust_asl = -1`，**当** 写入，**则** 被 `engine_thrust_nonneg` 拒绝。
3. **给定** `min_throttle = 120`，**当** 写入，**则** 被 `engine_min_throttle_range`（0–100）拒绝。
4. **给定** 一个引擎，**当** 它被某个 `Stage.engine` 引用，**则** 删除该引擎被 `PROTECT` 拒绝（防止级指向不存在的引擎）。
5. **给定** `series = 'AJ10'` 的 7 个引擎（`AJ10-27`/`-37`/`-42`/`-101A`/`-104`/`-138`/`-142`），**当** 按 `series` 筛选，**则** 7 条全部返回——证明用一列 `series` 就能替代被取消的 `EngineFamily` 表（brief §2）。

#### ③ 科学设备表（`parts.ScienceInstrument`）→ FR-PARTS-04

**落点**：`parts_scienceinstrument`（1:1 `PartCatalog`）｜ **无枚举**：`experiment_type` 为自由文本 ｜ 字段定义见 `03`（brief §4.5）

**验收标准**：

1. **给定** `transmit_efficiency = 40`、`is_repeatable = True`、`requires_surface = True`，**当** 保存，**则** 成功且详情页显示三个标记。
2. **给定** `transmit_efficiency = 150`，**当** 提交，**则** `clean()` 报错（`0 ≤ transmit_efficiency ≤ 100`）。
3. **给定** `has_storage = False` 而 `storage_capacity = 50`，**当** 保存，**则** 界面提示该容量不会生效（软提示，不阻断）。
4. **给定** 一个 `part_type = SCIENCE` 的部件，**当** 打开部件详情，**则** 显示科学设备子块。

#### ④ 在轨航天器（含轨道信息、周期信息）→ FR-SPACECRAFT-01 ~ 05

**落点**：`spacecraft_spacecraft`｜ **须支持的枚举**：`Situation` = `LANDED` / `SPLASHED` / `FLYING` / `ORBITING` / `ESCAPING` / `DOCKED` / `DESTROYED` ｜ 字段定义见 `03`（brief §4.14）

**验收标准（轨道信息）**：

1. **给定** `body = Kerbin`、`sma = 700000`、`eccentricity = 0.1`，**当** 打开详情页，**则** 显示计算出的 `rp = 630 000 m`、`ra = 770 000 m`（`r_p = a(1-e)`、`r_a = a(1+e)`）。
2. **给定** `eccentricity = 1.2`，**当** 提交，**则** 被校验拒绝（v1 只处理椭圆轨道 `0 ≤ e < 1`）。
3. **给定** `inclination = 200`，**当** 提交，**则** 被校验拒绝（`0 ≤ inclination ≤ 180`）。
4. **给定** `sma` 小于 `Body.radius`，**当** 提交，**则** `clean()` 报错（跨表规则，故用 `clean()` 而非 DB CHECK）。
5. **给定** 修改 `sma` 并保存，**当** 刷新页面，**则** 近/远拱点、周期、轨道速度同时变化——因为它们**不落库**（决策 D-12）。

**验收标准（周期信息）★这是本需求的核心**：

周期信息的实现方式由 **决策 D-12** 冻结为三段式：

| 角色 | 字段 | 说明 |
|---|---|---|
| **唯一权威输入** | `sma`（半长轴，m） | 周期的**唯一**输入源。配合 `Body.mu` 计算。 |
| **派生值（不落库）** | `period` | 由 $T = 2\pi\sqrt{a^{3}/\mu}$ 实时计算，**不建列**。理由：$T$ 是 $a$ 与 $\mu$ 的函数，独立存储必然漂移。 |
| **可选快照** | `cached_period_sec`（周期快照，s） | **玩家从 MechJeb / KER 抄录的周期快照**，仅作对照展示；界面并列显示「计算值 / 录入值」，**偏差 > 1% 时给出提示**。 |

**周期信息的验收判据**：

1. **给定** `body = Kerbin`（`mu = 3.5316e12`）、`sma = 3463331`，**当** 计算周期，**则** `T ≈ 21549.4 s`，与 `Body.sidereal_day` 偏差 **0.0000%**（brief §9.2 已实测回代验证）。
2. **给定** `body = Mun`（`mu = 6.513839e10`）、`sma = 3170557`，**当** 计算周期，**则** `T ≈ 138 984 s`。
3. **给定** `sma = 700000`、`mu = 3.5316e12`，**当** 计算周期，**则** `T ≈ 1958.1 s`（约 32.6 分钟）。
4. **给定** `sma` 为空或 `Body.mu` 为空，**当** 调用 `orbital_period()`，**则** 返回 `None` **而不抛异常**。
5. **给定** `cached_period_sec = 22000` 而计算值为 `21549.4`，**当** 打开详情页，**则** 页面同时显示两个值，并提示偏差约 **2.1% > 1%**。
6. **给定** 一个轨道周期，**当** 展示，**则** 同时给出「秒」与「天」两种单位（KSP 玩家惯用「天」，1 天 = `KERBIN_DAY = 21600.0` s）。
7. **给定** `situation = ESCAPING`（双曲线轨道），**当** 查看详情，**则** 不参与周期计算（`e ≥ 1` 时周期公式不适用）。

#### ⑤ 航天计划 1:n → FR-PROGRAM-01 ~ 04

**落点**：`programs_program`（「1」端）+ `programs_programlink`（「n」端）｜ **须支持的枚举**：`ProgramStatus` = `PLANNED` / `ACTIVE` / `COMPLETED` / `CANCELLED`；`ProgramObjectType` = `CARRIER` / `PAYLOAD` / `FLIGHT` / `SITE` / `SPACECRAFT` ｜ 字段定义见 `03`（brief §4.12、§4.13）

**基数的准确表述（必须严格按此理解，不得含糊）**：

> - `Program (1) ── (n) ProgramLink`：**1 个计划可挂任意多个成员**。
> - **一个成员对象最多归属 1 个计划**（由 5 条 `UniqueConstraint` 保证）。
> - 这是「1 计划 : n 对象」最贴合用户原话的实现——「1 航天计划」对「n 其他对象」。
> - **若将来需要「一个对象参与多个计划」，只需移除那 5 条唯一约束，表结构无需改动**（写入 `03` 的扩展说明）。

**验收标准**：

1. **给定** 计划 `PRG-DUNA-01`，**当** 依次把 2 枚火箭、3 个载荷、4 条发射日志挂入，**则** `/programs/<pk>/` 按 5 类分组展示这 9 个成员，且计划本身只有 1 行。
2. **给定** 火箭 `LV-DAVY2B` 已归属 `PRG-DUNA-01`，**当** 尝试把它再挂到 `PRG-MUN-02`，**则** 被 `uniq_program_carrier` 唯一约束拒绝。
3. **给定** 一行 `ProgramLink(object_type='CARRIER')`，**当** 同时置 `carrier` 与 `flight` 非空，**则** 触发 `programlink_exactly_one_object` 检查失败。
4. **给定** 一行 `ProgramLink(object_type='FLIGHT')` 但 `flight` 为空，**当** 写入，**则** 同样被 `programlink_exactly_one_object` 拒绝。
5. **给定** 删除计划 `PRG-DUNA-01`，**当** 确认，**则** 其全部 `ProgramLink` 级联删除，而**成员对象本身（火箭/载荷/发射日志等）全部保留**。
6. **给定** 删除火箭 `LV-DAVY2B`，**当** 确认，**则** 指向它的 `ProgramLink` 级联删除，计划本身**不受影响**。
7. **给定** 一个计划，**当** 打开总览页，**则** 显示由 `services/stats.py` 计算的进度（各状态计数）、预算执行率（`spent / budget`）与发射成功率。

#### ⑥ 火箭与载荷的级结构（1 火箭 n 级、1 级 n 燃料罐或引擎）→ FR-STAGE-01 ~ 03、07

**落点**：`stages_stage`（级）+ `stages_stagetank`（级-燃料罐挂载）｜ **须支持的枚举**：`StageOwnerType` = `CARRIER` / `PAYLOAD`；`SeparationType` = `STACK_DECOUPLER` / `RADIAL_DECOUPLER` / `DOCKING` / `NONE` / `OTHER`；`MountPosition` = `INLINE` / `RADIAL` ｜ 字段定义见 `03`（brief §4.8、§4.9）

**结构与基数的准确表述**：

```
CarrierModel (1) ──┬── (n) Stage ──┬── (1) Engine  × engine_count
PayloadModel (1) ──┘               └── (n) StageTank ── (1) FuelTank × quantity
```

- **1 枚火箭 n 级**：`Stage.carrier` → `CarrierModel`，`related_name='stages'`。
- **1 个载荷 n 级**：`Stage.payload` → `PayloadModel`，`related_name='stages'`。**火箭与载荷共用同一张 `Stage` 表**——两者级以上语义完全一致，避免抄两张平行表（这是相对参考项目 `ek` 的改进：`ek` 的 `LV` 与 `Aircraft` 就是两份近乎重复的代码）。
- **1 级 n 个燃料罐**：`StageTank.stage` → `Stage`，`related_name='tanks'`；同型燃料罐用 `quantity` 压缩为一行（如 4 个 FL-T800 = 一行 `quantity=4`），异型多行。
- **1 级 n 个引擎**：由 `Stage.engine` + `Stage.engine_count`（默认 1）表达，`is_radial_engine` 标记是否径向安装。

**验收标准**：

1. **给定** 火箭 `LV-TEST`，**当** 添加 3 个级（`stage_order` = 1/2/3），**则** 详情页按序自上而下显示 3 个级及其逐级 Δv。
2. **给定** 同一归属下已有 `stage_order = 2`，**当** 再插入一个 `stage_order = 2`，**则** 被 `uniq_carrier_stage_order` 拒绝。
3. **给定** 一个级，**当** `stage_order = 0`，**则** 被 `stage_order_positive` 拒绝。
4. **给定** 一个级，**当** 挂 2 种燃料罐：FL-T800 × `quantity=4`（`INLINE`）与 FL-T400 × `quantity=2`（`RADIAL`），**则** 只需 2 行 `StageTank` 记录 6 个罐。
5. **给定** 同一级、同一燃料罐、同一 `mount_position` 再挂一行，**则** 被 `uniq_stage_tank_mount` 拒绝；**但**同燃料罐换 `RADIAL` 挂载则允许。
6. **给定** `quantity = 0`，**当** 提交，**则** 被 `stagetank_quantity_positive` 拒绝。
7. **给定** 删除一个级，**当** 确认，**则** 其 `StageTank` 记录**级联删除**，但被引用的 `FuelTank` 部件**保留**。
8. **给定** 一个被 `StageTank` 引用的 `FuelTank`，**当** 尝试删除该燃料罐，**则** 被 `PROTECT` 阻止。
9. **给定** 火箭编辑页，**当** 点击「+ 添加一级」并在级内挂载燃料罐，**则** 保存后火箭详情页的 Δv 计算把该级燃料质量计入 `m_0`（`本级燃料质量 = Σ(FuelTank.capacity × quantity) × FUEL_UNIT_MASS`）。
10. **给定** `owner_type='PAYLOAD'` 但 `carrier` 非空，**当** 写入，**则** 触发 `stage_exactly_one_owner` 失败。

## 8. 非功能需求

编号格式 **`NFR-<类别>-<序号>`**。

### 8.1 性能 NFR-PERF

| 编号 | 需求 | 判据 |
|---|---|---|
| NFR-PERF-01 | 单机、单人、低并发场景。不做缓存、不做异步任务队列、不做连接池调优。 | 全站无 Redis / Celery / 消息队列依赖。 |
| NFR-PERF-02 | 页面响应 **< 1 s**（本机、SQLite）。 | 在约 10³ 量级数据下，列表页与详情页首次响应 < 1 s。 |
| NFR-PERF-03 | 列表页必须**分页**。 | 发射日志列表、部件库列表均分页展示。 |
| NFR-PERF-04 | 热点查询必须有索引支撑。 | 明细见 `03`：`(state, planned_ut)`、`(body, is_active, situation)`、`(part_type, diameter)`。 |
| NFR-PERF-05 | 轨道与 Δv 计算为**纯内存计算**，单次调用应为微秒~毫秒级。 | `services/orbital.py` 的函数无数据库访问。 |

### 8.2 数据完整性 NFR-DATA

| 编号 | 需求 | 判据 |
|---|---|---|
| NFR-DATA-01 | 完整性约束**优先在数据库层强制**：外键、`CHECK`、`UNIQUE`。 | brief 各表约束（如 `stage_exactly_one_owner`、`programlink_exactly_one_object`、`uniq_carrier_stage_order`）全部落到 migrations。 |
| NFR-DATA-02 | **删除策略必须显式声明**，不得依赖默认行为。 | 全表策略见 brief §4.16：`PROTECT`（引擎/燃料罐被引用、天体被发射场引用、发射历史）、`CASCADE`（级随火箭、`StageTank` 随级、`ProgramLink` 随计划或对象）、`SET_NULL`（`derived_from`、`Spacecraft.source_*`）。 |
| NFR-DATA-03 | **跨表规则用模型 `clean()`，不用跨表 `CHECK`**。 | 如 `FuelTank.wet_mass >= part.dry_mass`、`sma > Body.radius`：SQLite 的 `CHECK` 不支持子查询。 |
| NFR-DATA-04 | 业务规则给出**友好中文错误提示**，不使用数据库异常直接抛给用户。 | 如 `FlightLog` 的「`state=PLANNED` 时 `actual_ut` 应为空」写在 `clean()` 而非 CHECK。 |
| NFR-DATA-05 | 时间语义**统一为 KSP 游戏时间 `UT`**（游戏内秒，`FloatField`）。 | 全项目**不使用** `DateField`/`DateTimeField` 表达游戏时间；`created_at`/`updated_at` 是现实世界时间，仅用于管理，不参与业务语义。 |
| NFR-DATA-06 | 单位统一：质量 **吨(t)**、推力 **kN**、比冲 **秒(s)**、距离 **米(m)**、角度 **度(°)**、造价 **根币(√)**。 | 字段级定义见 `03`；任何非上述单位须显式换算并记录。 |
| NFR-DATA-07 | 数据库变更有**版本化迁移**。 | 使用 Django migrations；**禁止 `DROP DATABASE` 重建**（旧系统缺陷 #13）。 |
| NFR-DATA-08 | 涉及多表写入的操作使用 `transaction.atomic()`。 | 如「一键执行发射」、级 FormSet 保存。 |
| NFR-DATA-09 | v1 **不使用软删除**。 | 删除即删除；不可删的记录由 `PROTECT` 从数据库层拦住。 |

### 8.3 可移植性 NFR-PORT

| 编号 | 需求 | 判据 |
|---|---|---|
| NFR-PORT-01 | 数据存于**单个文件** `db.sqlite3`，可直接拷贝备份。 | 关闭服务后复制 `db.sqlite3` 即完成备份；`db.sqlite3` 进入 `.gitignore`。 |
| NFR-PORT-02 | 未来可切换到 **MySQL 8.4**（约 1 小时）或 PostgreSQL。 | 只需改 `DATABASES` + 安装驱动 + 重跑 `migrate`；已有数据需 `dumpdata`/`loaddata`。 |
| NFR-PORT-03 | **代码中不出现裸 SQL**，全部通过 Django ORM。 | 全项目 grep 不到手写 SQL 字符串拼接（旧缺陷 #3 的根治手段）。 |
| NFR-PORT-04 | 多态实现必须**在 SQLite 与 MySQL 上均可移植**。 | 使用 `owner_type` + 双可空 FK + CHECK；**不使用 `GenericForeignKey`**（`ContentType` 无法建立数据库级外键与 CHECK）。 |
| NFR-PORT-05 | 前端**无构建链**。 | 不引入 React/Vue/webpack/vite；JS 为原生脚本文件直引（决策 D-13）。 |

### 8.4 可维护性 NFR-MAINT

| 编号 | 需求 | 判据 |
|---|---|---|
| NFR-MAINT-01 | **分层架构**：模型层 / 服务层 / 表单层 / 视图层 / 管理后台 / 路由层，职责见 brief §5.2。 | 视图层**只做编排**（取数 → 调服务 → 渲染），**不写业务规则**；模型层不写 HTTP 逻辑。 |
| NFR-MAINT-02 | `services/` **独立于任何 app**，且**不 import Django 视图或 request**。 | `services/orbital.py`、`services/deltav.py`、`services/stats.py` 可被 Admin、视图、管理命令、单元测试共同复用。 |
| NFR-MAINT-03 | 入口拆分：`manage.py` **只保留 Django 标准入口**。 | 旧项目 992 行 / 26 路由的巨石入口被 `config/` + 9 个 app 取代。 |
| NFR-MAINT-04 | 命名与文案规范：Python 字段 `snake_case`、类名 `PascalCase`、每个字段带中文 `verbose_name`、每个模型带中文 `Meta.verbose_name(_plural)`。 | 抽查任意模型与字段，均存在中文标签。 |
| NFR-MAINT-05 | 物理常数**集中定义**在 `core/constants.py`，不得散落硬编码。 | 至少包含 `G0 = 9.80665`、`FUEL_UNIT_MASS = 0.005`、`KERBIN_DAY = 21600.0`。 |
| NFR-MAINT-06 | 依赖面尽可能小。 | `requirements.txt` 仅 `Django==5.2.*` 与 `numpy>=1.26`；**不再需要** PyMySQL / WTForms / passlib。 |

### 8.5 可测试性 NFR-TEST

| 编号 | 需求 | 判据 |
|---|---|---|
| NFR-TEST-01 | `services/` 三个模块**必须有单元测试**，通过 `manage.py test` 运行。 | brief §8.7 明列最低覆盖项，见下。 |
| NFR-TEST-02 | 计算类测试必须覆盖**四个最低用例**。 | ① Kerbin 同步轨道周期 ≈ `sidereal_day`；② Mun 轨道周期与 KSP Wiki 参考值比对；③ 单级 Δv 手算样例（`isp=345`,`m0=10 t`,`mf=4 t` → `≈ 3100.1 m/s`）；④ `mu` 为空或 `sma` 为空时返回 `None` 而非抛异常。 |

### 8.6 安全性 NFR-SEC

| 编号 | 需求 | 判据 |
|---|---|---|
| NFR-SEC-01 | **CSRF 防护**：使用 Django CSRF 中间件（默认开启）；所有写操作必须 **POST**。 | 删除类操作使用 `DeleteView`（仅接受 POST），**修复旧系统 GET 删除 + 无 CSRF 的缺陷**。 |
| NFR-SEC-02 | **密码哈希**：使用 Django 内置 PBKDF2。 | 不使用 `sha256_crypt`；旧用户哈希不兼容属已知风险（R-04）。 |
| NFR-SEC-03 | **无 SQL 注入**：全部通过 ORM 参数化查询。 | 对应 NFR-PORT-03；旧系统 `manage.py:908` 的注入点被根治。 |

## 10. 约束与假设

### 10.1 领域约束

| 编号 | 约束 / 假设 | 影响与出处 |
|---|---|---|
| C-01 | **KSP 版本以 1.12.x 为准**。天体常数取自 KSP 官方 Wiki 交叉核对。 | 若游戏版本更新，或使用 **RSS / OPM** 等天体模组，需重新采集常数。`Body` 表设计为**可编辑**正是为此——天体常数是**数据**而非硬编码（风险 **R-01**，brief §9.1）。 |
| C-02 | **`FUEL_UNIT_MASS = 0.005 t/单位` 是混合平均简化**。 | `LF_OX` 的 `capacity` 是 LF + OX **合计**单位数，统一按 0.005 t/单位 折算，**不做 LF/OX 分账**。对「本级总质量 → Δv」足够精确，且与新版本 KSP 的 LF/OX 统一密度一致。**Δv 计算存在系统性偏差（量级正确）**，`06` 必须标注为已知简化（风险 **R-02**）。 |
| C-03 | **`capacity` 与质量的换算关系**：`capacity` = 燃料资源单位数；1 单位 ≈ **0.005 t = 5 kg**。`SOLID` 的 `capacity` 直接等于固体燃料质量换算单位，乘同一系数。 | 以 `FUEL_UNIT_MASS = 0.005` 与 brief §4.3 的换算说明为准。 |
| C-04 | **Δv 公式中的 `G0 = 9.80665 m/s²` 是常数，与所在天体无关**。 | 常见错误是用当地重力 `g_local` 代入齐奥尔科夫斯基公式，**必须避免**（brief §8.1）。 |
| C-05 | **推重比中的 `g_local = μ / r²` 是当地重力**，v1 在发射场判定时取 `r = Body.radius`。 | 与 C-04 是两个不同的 g，不可混用（brief §8.2）。 |
| C-06 | **判定阈值**：起飞级 `TWR ≥ 1.2` 视为可用；`1.2 ≤ TWR ≤ 1.7` 为合理区间；`> 2.5` 提示「过推，气动损失大」。 | brief §8.2。 |
| C-07 | **周期公式 $T = 2\pi\sqrt{a^3/\mu}$ 中的「日」用恒星日（`sidereal_day`）**。 | KSP 社区常引用的「同步轨道高度 2 868.75 km」对应的是**太阳日 21 600 s**，而正确答案是 **2 863.33 km**（恒星日 21 549.4 s）。`Body` 表同时保留 `sidereal_day` 与 `solar_day` 两列，正是为了消除这一混淆（brief §8.5）。**`06` 须明确：周期自洽性验算用恒星日。** |
| C-08 | **展示层「天」换算用 `KERBIN_DAY = 21600.0` s（太阳日）**，与 C-07 的恒星日**不是同一个量**。 | 二者用途不同（展示换算 vs 同步轨道计算），文档与界面都需注意不要混用。 |
| C-09 | **`sma` 必须取「被天体环绕的轨道半长轴」，而非该天体的公转轨道半径。** | brief §9.2 明确记录了一次真实教训：起草时曾把公转轨道半径当作 `sma` 代入，得出错误参考值。故单元测试**优先采用同步轨道自洽性用例**——它只用天体自身的 `mu` 与 `sidereal_day`，不存在量混用的空间。 |
| C-10 | **v1 只处理椭圆轨道**：`0 ≤ e < 1`。 | `situation = ESCAPING`（双曲线/抛物线轨道）**不参与周期计算**（brief §4.14）。 |
| C-11 | **`result_code` 语义照搬 `ek.Launch` 的编码**：`NULL`=尚未执行、`-2`=台架中止、`-1`=任务失败、`0`=成功、`>0`=第 n 级失效。 | 必须写入模型 `help_text`，使录入者不查文档即知含义（brief §4.11）。 |
| C-12 | **`SCP-` 前缀保留**：旧表 `SCP` 的名字不再作为表名，但任务编号前缀保留，使旧数据与界面习惯延续。 | brief §4.15。 |
| C-13 | **「族」表全部取消**（`EngineFamily`/`StageFamily`/`CarrierFamily`/`PayloadFamily`），用 `series` + `derived_from` 两列替代（决策 D-08）。 | 论证见 brief 第 2 节：族只携带「名称 + 描述」，n 端无可共享的实质属性，属**可消除的传递依赖**。而 `PartCatalog` **保留**——它携带所有部件类型真正共享的属性，是真正的 1:1 超类。 |
| C-14 | **「级间段」= 火箭的「级」（`Stage`）**，不是 interstage/decoupler 零件（决策 D-07）。 | 依据用户原话「1 级有 n 燃料罐或引擎」。 |

| 术语 | 含义 |
|---|---|
